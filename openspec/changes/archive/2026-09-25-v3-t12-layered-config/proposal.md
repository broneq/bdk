# Proposal

## Why

Plan: docs/V3-IMPLEMENTATION-PLAN.md, T12. Tracks #50.

The kernel has a reading half of the configuration (T11: `shared/config` finds and parses the three YAML files) and nothing else: no schema, no merge, no validation, no `config` command. Every later slice needs typed, validated settings (T13 `ctx` first), and the user condition on R-format (JSON Schema for the IDE) is unmet. v2 keeps its settings in `.bdk/settings.json`, read by `scripts/get_settings.py`, the three `inject*.py` scripts and `hooks/check-bdk-config/check.py` against a hand-written `settings.schema.json`; v3 needs one source for the kernel and the skills, with unknown keys and keys without a consumer rejected (S6). Like the CLI contract (T10) and the state schema (T14), the settings get a first-class document before any code: the whole key tree is designed now, so no later task invents a colliding or inconsistent name.

## What Changes

- **New spec `kernel-settings`**, written as the first task group and accepted by the user before any code of this Change: the four layers and their files, the merge, kebab-case naming and `id` addressing, the tool entry shape, prompt values, the snapshot, the JSON Schema and modeline, the removed v2 keys, and the **full v3 key tree** with type, default, owner task, consumer slice and v2 origin per key, including the keys of T21 to T31. Schema only: an owner task registers its keys when its consumer lands and may amend its rows through a delta.
- **Four layers** (A-warstwy, D4): bundle defaults < global (`$XDG_CONFIG_HOME/bdk/settings.yaml`, else `~/.config/bdk/settings.yaml`; `%APPDATA%\bdk\settings.yaml` on Windows) < `.bdk/settings.yaml` < `.bdk/settings.local.yaml`. Deep merge; arrays of objects with `id` merged by `id`, other arrays replaced whole; full override allowed (D4).
- **Module registry** in `shared/config` (zod): a slice declares the settings it reads in its own `config.ts`; the composition root assembles the registry. T12 registers only keys whose consumer exists or lands next (user decision Q2): `languages`, `tools.{test,lint,build}`, `features.lavish` (consumer `ctx`), `prompts.{dir,files}` (consumer `shared/config`) and the `rules/*` prompt keys. Every error names the key, the layer and the file. A key the spec declares for a task that has not landed is refused with `policy/unknown-config-key` naming the owner task; a removed v2 key is refused naming its replacement; any other unknown key gets a "did you mean" hint. A structural test enforces S6 (the module names its consumer slice, which reads it once it has a handler), and a contract test keeps the spec's key tables and the registry equal.
- **Tool entries** gain `when`: free text that tells the model when that command is the right one (user decision). `id` replaces v2's `type`; `tier` is required for test and lint.
- **Kebab-case everywhere** (user decision Q5): key segments, ids and enum values; the plan's `rules.propose_when` and `rules.max_per_package` become `rules.propose-when.*` and `rules.max-per-package` in the plan and the inventory.
- **Markdown values** (`prompts/`, R-format): one file per prompt key with frontmatter `mode: extends|replace` and `applies`. Each layer has its own prompts directory, movable with `prompts.dir`, and single keys can point at any file with `prompts.files.<key>` (user decision Q4). v2 `quality.<category>` and `language-rules.<lang>` become the prompt keys `rules/<category>` and `rules/languages/<lang>` (Q3).
- **Resolved snapshot** `.bdk/.machine/config/resolved.yaml` with the personally overridden keys (names only; D4b).
- **JSON Schema export** from zod: `schema/settings.json` plus the `schema/cli/` files whose zod exists (`version`, `doctor`, the refusal, `config-*`), regenerated by `pnpm build`, guarded by `git diff --exit-code dist/ schema/` on CI. Modeline `# yaml-language-server: $schema=https://raw.githubusercontent.com/broneq/bdk/v<plugin version>/schema/settings.json`; offline copy `.bdk/.machine/schema/settings.json`.
- **`config` commands**: `show` (text mode prints YAML), `check`, `schema`, `set --global | --local` (`set` keeps comments). Contract fix: `config check` answers an error with the refusal (exit 2) and returns only warnings on exit 0 (`missing-modeline`, `schema-outdated`, `legacy-settings`); without `.bdk/` it writes nothing.
- **`doctor`** gains the schema modeline and offline copy checks and their `--fix` repair.
- **v2 readers switched to the kernel** (**BREAKING** on `staging/v3`, user decision Q1): `scripts/get_settings.py`, `hooks/check-bdk-config/` (`check.py`, `settings.schema.json`) and their tests are deleted. The eight skill `!` blocks that called `get_settings.py` call `bdk config show tools.<kind>` with the `|| echo "BDK STOP..."` wrapper, and their `allowed-tools` carry the node rule. The SessionStart hook runs `bdk config check` in a BDK project. `inject.py`, `inject-rules.py` and `inject-language-rules.py` read flags, languages and rule overrides from `bdk config show --json` through one small Python bridge until T13 deletes them. `setup` writes `.bdk/settings.yaml` with the modeline instead of `settings.json`. Docs, `.claude/rules/` and `STARTUP_INSTRUCTIONS.md` describe the YAML settings and prompt values.

Resolutions of the plan's "To resolve in the spec" (details and alternatives in design.md):

- **Full list of v3 keys**: the `kernel-settings` spec, one requirement per key group.
- **XDG on Windows**: `%APPDATA%\bdk\`; elsewhere `$XDG_CONFIG_HOME/bdk/` when set and absolute, else `~/.config/bdk/`.
- **Versioned schema URL**: the release tag of the plugin version, `https://raw.githubusercontent.com/broneq/bdk/v<version>/schema/settings.json`.
- **Key without a consumer, technically**: the module names its consumer slice and lives in that slice's `config.ts`; a structural test checks the declaration and, once the slice has a handler, that a use case reads the module.
- **v2 key mapping** (for T32's import): the "v2 origin" columns and the "Removed v2 keys" table of `kernel-settings`.
- **Physical deletion** of `get_settings.py` and `settings.schema.json`: in T12, not T32 (Q1).

Inputs carried by citation: design "Configuration (A-warstwy, R-format, D4, B7-B10)", "Change directory", "Loop protection", "Verifier contracts (P8)", "CLI contract" (wrapper form), "What We Did NOT Decide" (Windows path for XDG); decision register D4, D4b, S6, A-warstwy, R-format (user condition: JSON Schema for the IDE), R-11, P11; specs `kernel-cli`, `kernel-cli/config`, `kernel-cli/service`, `kernel-architecture`, `plugin-tooling`; T02 key additions (docs/V3-SKILL-INVENTORY.md, T12 row); ADR-0001.

Out of scope:

- Code of keys owned by later tasks: `policy.*` (T21, T22, T23), `execution.*` and `archive.*` (T23), `rules.*` (T31), `spec.*` (T30). Their schema is designed here; each owner registers its module.
- `ctx`, `hooks session-start` and the deletion of `inject*.py` and the static STARTUP hook (T13); the `!` blocks this Change writes are replaced by `ctx skill` there.
- The `setup` redesign (T41); T12 changes only the file `setup` writes.
- Writing the overridden-key list into a Change (T20); `.gitignore` entries for `.bdk/.machine/` and `.bdk/settings.local.yaml` (T20, T32).
- `bdk import` of `settings.json` (T32). Until then a v2 project on `staging/v3` runs with defaults, and `config check` and `doctor` name `bdk import`.
- JSON Schema of the Change state (T14, reusing this generator).

## Capabilities

### New Capabilities

- `kernel-settings`: settings files, layers, merge, naming, tool entries, prompt values, snapshot, JSON Schema and modeline, removed v2 keys, and the full v3 key tree.

### Modified Capabilities

- `kernel-cli`: Output modes names the `allowed-tools` pair that pre-approves the content wrapper, correcting the `allowed-compound` citation (HOST-FACTS `wrapper`, `wrapper-old-rule`).
- `kernel-cli/config`: the four commands (YAML text output of `show`, prompt values, `check` exit semantics and warnings, `set` preserving the file, `schema --url`), referring to `kernel-settings` for the configuration itself.
- `kernel-cli/service`: `bdk doctor` gains the schema modeline and offline copy checks and their `--fix` repair.
- `kernel-architecture`: slice anatomy (a slice's `config.ts`), `shared/config` holdings, tests per slice (S6 consumer test, generated schemas), CI pipeline (`git diff --exit-code dist/ schema/`).
- `plugin-tooling`: settings are read only through the kernel; the SessionStart settings check runs `bdk config check`; the removed-key warning of `check.py` is replaced.
