# Design

## Context

See proposal.md, Why. This is part C of T23. The decisions T23-D0 to D24 and the spike facts live in the part A design (`openspec/changes/archive/2026-09-28-v3-t23a-roles-adapters/design.md`), D25 to D38 in the part B design (`openspec/changes/archive/2026-09-28-v3-t23b-dispatch-envelope/design.md`); this design cites them and adds T23-D39 onwards. Five decisions were taken by the user in a Lavish review on 2026-09-28 (`.lavish/v3-t23c-questions.html`), each with a worked example.

State today:

- `evidence record` and `evidence check` exist as index records, a spec and output schemas, but no handler: running them answers `input/unknown-command`. The manifest schema (`kernel/src/shared/store/state/evidence.ts`) and its layout paths (`registry.ts`) exist; there is no `kernel/src/evidence/`.
- `attempt close` declares `policy/stale-evidence` and `policy/missing-citation` and emits neither. `nextRung` (`attempt/domain/ladder.ts`) returns `post-task-steps` on `ok`.
- The `post-task-step` kind (`graph/domain/kinds/steps.ts`) is a fileless stub; `pipeline/pipeline.yaml` has no step nodes. The engine names an instance `<kind>:<nn>`, so two nodes of one instanced kind would collide.
- `dispatch build` removes a ticket's earlier packages, and every ticket-keyed agent command (`dispatch show <ticket>`, `rules show --ticket`, `log add --ticket`, `log ingest --ticket`) resolves the role through the ticket's only package (`ticketDispatch` in `shared/store`).
- `execution.concurrency` and `archive.keep-evidence` are planned keys (owner T23); `policy.evidence` does not exist.
- HOST-FACTS: forked skills do not run concurrently under `claude -p` (`fork-concurrency`); nested agents work (`nested-agents`); `SendMessage` reaches `main` (`send-to-main`).

## Goals / Non-Goals

**Goals:**

- A task's ticket closes `ok` only on evidence that is fresh against the code it covers and cites the value that shows a pass (P5, T4).
- The post-task steps and their order are data in `pipeline.yaml` that the kernel enforces, not prose in a skill (T23-D9).
- A swarm skill that `execute` and `cr` can follow with nothing but packages, the ledger and the kernel's answers.

**Non-Goals:**

- `change close` and the call of the prune (T30); the stage skills that run the swarm (T41 `execute`, T42 `cr`); UI evidence (`ui-verify`, after v3); guard hooks (T24); nested agent trees (no adapter carries the Agent tool in 3.0).

## Decisions

- **T23-D39 One Change for all of part C (user choice).** Evidence, steps, swarm and prune ship in `v3-t23c-evidence-post-task-swarm`, as the plan has it. Alternative: split into evidence-steps and swarm-prune - rejected by the user; one verification round, and the swarm is written against the step mechanism in the same PR.
- **T23-D40 Three step kinds, one node per part, done from evidence (user choice).** `simplify`, `tests-scoped` and `lint` are kinds on one `post-task-step` base, because the engine names instances by kind and one kind for three nodes would collide on `post-task-step:02`. Each has one instance per plan part and sits after `execute` in `pipeline.yaml` (simplify, then tests-scoped and lint), and `review` requires them. A step node is done when the latest manifest of its kind covering the part (target a task of the part, the part or the Change) is fresh against its own target and says `pass` or `not-run`; it is stale when that manifest is not fresh. There is no done transition: a review-fix ticket re-records evidence for the Change, and a transition written by `part done` could not follow it without a new command. An instance of a step node requires the instance of its own number of each collection it requires; other instanced kinds keep requiring whole collections, so `execute-part` semantics do not change. The registry grows from 13 to 15 kinds and `pipeline/post-task-step.md` is replaced by `pipeline/simplify.md`, `tests-scoped.md` and `lint.md`. Alternatives: steps once per part - rejected by the user, a failure of `02-1` surfaces after `02-3`; a node per task - rejected, it breaks T23-D7 (risk R3) and adds three nodes per task; instance ids by node id - rejected, it renames every existing instance (`plan-part:01`).
- **T23-D41 Steps run inside the task's ticket, `ok` requires evidence (user choice).** The orchestrator dispatches the implementer, then the ticket's `steps` (from `attempt open`, in pipeline order) under the same ticket, then closes it. An `ok` close of a code ticket (one holding an `implementer` package) checks each step kind: the ticket's latest manifest exists and says `pass` or `not-run` (`policy/missing-evidence` otherwise, new), is fresh (`policy/stale-evidence`), and a `pass` carries a citation and its committed files still match (`policy/missing-citation`). Failing tests are a `fail` close and the existing ladder narrows, escalates or parks; no new loop or budget. `next.action` after `ok` becomes `commit`. A `not-run` step is accepted while the part holds at most `policy.budgets.not-run` `not-run` manifests of that kind, read by `attempt`, which owns `policy.budgets`; the graph cannot read budgets (no `graph -> attempt` edge), so the budget is enforced at close and the node trusts what close accepted. Alternative: a ticket per step in a new `post-task` loop - rejected by the user, a failed step has no natural fixer and two ladders count one bug.
- **T23-D42 One package per role and ticket, the active package names the role.** `dispatch build` keeps the packages of the ticket's other roles and stamps the new one as `package` in the attempt record; every ticket-keyed agent command resolves the role through it. The orchestrator builds the next package only after the agent of the active one returned and any resume ended, which the swarm skill states. `rules-read` is stamped only under the implementer package, so a simplifier or runner reading rules cannot hide an implementer that read none (R2). Alternatives: a `--role` flag on every ticket-keyed command - rejected, every role body and package changes and the flag can disagree with the package; the newest package by `at` - rejected, `at` has second precision and two builds of one ticket fall in the same second in tests.
- **T23-D43 `simplifier` is an eighth role on `worker` (realises T23-D9's simplify package).** A package varies by role (T23-D11), so the simplify step is a role with its own contract: simplify the uncommitted diff without changing behaviour, within `Files:`, with the implementer's working-tree sentence (T3), rules as the implementer's. `attempt close ok` records the `simplify` manifest from the stored simplifier report (`source: kernel`, report as its file, `pass` for `done`/`done-with-concerns`, `not-run` for `blocked`/`needs-context`); kernel evidence needs no citation. Alternatives: the simplifier records its own evidence - rejected, a transformation has no measured value to cite; `log ingest` records it - rejected, `log` is a leaf and cannot import `evidence`; a `step` field on the implementer package - rejected, the package would embed the implementer body with contradicting instructions.
- **T23-D44 One runner package runs both checks.** The runner package gets a `Checks` section: per step kind the runner runs, the configured `tools.test` (tier `fast`, `related` then `scoped` then `command`) or `tools.lint` commands (`scoped` then `command`) with `{files}` replaced by the target's executable files, their `when` texts, and the exact `evidence record` line. A kind without a command is recorded `not-run` with the reason. `dispatch -> ctx` is added for the tool entries `ctx` owns. Alternatives: a runner per check - rejected, two haiku dispatches per task for two commands; the runner reads `bdk config show tools.*` - rejected, the package must be self-sufficient (T23-D0) and the scoping by executable files is kernel logic.
- **T23-D45 Tree hash.** The scope of a target is its part (task), the part, or every part (Change); covered files are the scope's `Files:` minus `policy.evidence.non-executable`, plus every non-ignored working-tree file matching `policy.evidence.build-config` (build config wins). sha256 over the sorted paths, each with a NUL, its file hash or the marker `absent`, and a NUL, so the boundaries between files are unambiguous. The manifest stores `tree` (path and hash per file) so `evidence check` can name `changedSince`. One function in the `evidence` slice serves record, check, close and the step nodes (`graph -> evidence` and `attempt -> graph` added; `evidence` stays a leaf). Alternatives: hash the whole working tree - rejected, any unrelated edit makes every manifest stale; only the task's `Files:` - rejected, T23-D7 and risk R3.
- **T23-D46 Storage by size and type (user choice).** UTF-8 text without NUL up to `policy.evidence.max-committed-bytes` (65 536) is copied to `evidence/<target>-<evidenceId>-<name>` and committed; anything else stays in `.bdk/.machine/evidence/`, referenced by hash. The layout row for captures changes from `<evidenceId>.<ext>` to `<evidenceId>-<name>`, because one manifest can commit several files with the same extension. Citations resolve only where the file exists, so committed reports stay checkable on every clone. Alternatives: always `.machine` - rejected, a reviewer sees only hashes; always commit - rejected, binaries grow the history.
- **T23-D47 Citation grammar (T23-D8).** `<file>#<json-pointer>`, `<file>:<line>`, `<file>:<line>=<text>`; `<file>` by recorded path or file name, optional with one file; a bare `/pointer` is `#/pointer`, keeping the existing example valid, unless it starts with a recorded file's path (an absolute path, found in the live check of 9.2). A non-text file is not citable. Every citation must resolve, and `pass` needs one. `evidence record` validates; `attempt close` re-checks presence and committed hashes, and the verdict kinds check the evidence their report lists (`done` keeps `policy/missing-citation` from the rule table).
- **T23-D48 `policy.evidence` lists append-only (user choice).** Two glob lists with the defaults of the review plus `max-committed-bytes`, consumer `evidence`. `kernel-settings`, Merge, gains the append-only array: layers add items and never remove defaults, as P8's categories behave. A documentation repository that builds its Markdown lists it in `build-config`, which wins. `.claude/rules/verification-scoping.md` names the kernel lists as one more copy of the file-class partition. Alternative: projects replace the list - rejected by the user, a project could silently drop `package.json` from freshness.
- **T23-D49 `log list --since-ticket-start <ticket>`.** Entries with `at` at or after the ticket's `opened-at`, open or closed ticket; the swarm reads what other agents logged during a wave. Second precision means an entry written in the second the ticket opened is included, which errs towards showing too much.
- **T23-D50 Swarm skill as principles plus one host note.** `skills/swarm/SKILL.md` (not user-invocable, with context lines) states isolation by disjoint `Files:`, the package path as the prompt, concurrency from the context, the ledger as the channel, steps under the ticket, the single resume and a flat swarm; `references/hosts/claude-code.md` holds the host mechanics (several Agent calls in one message run concurrently, forks do not under `-p`, `SendMessage` reaches `main` and resumes an agent). No adapter carries the Agent tool in 3.0, so there is no tree of agents yet; the principle stays so a later host note can enable it. Tested by a content test (the resume wording covers role-contracts' `one resume for a missing report` scenario, deferred from B by T23-D35) and an eval in `tests/evals/skills/swarm/`. Alternatives: the orchestration in kernel code - rejected, the kernel runs no agents (T23-D6); per-stage copies in `execute` and `cr` - rejected, two copies drift.
- **T23-D51 Acceptance with a fake evidence kind.** A test kind `contract-snapshot` on the step base, in a test pipeline after `execute`, records `not-run`, then `pass` with a citation, and goes stale on a `Files:` edit, which exercises manifest, `not-run`, citations and freshness through the unchanged graph commands (T21 kind extensibility).
- **T23-D52 `execution.concurrency` is consumed by `ctx`.** The only reader is the swarm skill, and a skill gets settings-derived content only through `bdk ctx skill` (`.claude/rules/skill-context.md`); a `concurrency` manifest part renders it. With consumer `dispatch`, the S6 test would fail, since no dispatch use case reads it. Alternative: a field in `dispatch build`'s output - rejected, it is not a property of one package.
- **T23-D53 Prune in `shared/store`, `archive.keep-evidence` moves to T30.** The prune function writes `pruned.md` (path, hash, bytes per removed file; new `pruned` document kind) in `dispatch/` and `reports/` and removes the bodies; `change close` of T30 calls it without a slice edge. The key's module is registered by the task that lands its consumer (`kernel-settings`, Registry and consumers), and registering it now would fail the S6 test, so its owner becomes T30 and the `key of a later task` scenario now names T30. Alternatives: register the key under `change` now with a status line reading it - rejected, a reader invented to satisfy a test; prune in the `change` slice - rejected, T30 owns that slice's close use case and the prune must be testable now.
- **T23-D54 `evidence check` takes any target.** The argument widens from a task to a task, part or Change id or an `E-` id, because review-fix tickets target the Change and the step nodes need the same check per part.
- **T23-D55 Scenario names of MODIFIED requirements are kept (as T23-D36).** `seven roles discovered` keeps its name and now lists eight roles.

## Risks / Trade-offs

- [Three agents per task (implementer, simplifier, runner)] → The user accepted it for early failure detection; the runner is on the cheap `haiku` adapter, and `execution.concurrency` caps a wave.
- [A flaky lint consumes the task's budget] → A `fail` close walks the ladder like any failure; `not-run` with a reason is the honest answer to a broken tool, and its budget is `policy.budgets.not-run`.
- [Build-config listing walks the working tree] → One `git ls-files -co --exclude-standard` per hash, matched against a short glob list; the E2E perf budget covers `attempt close`.
- [The active package changes under a running agent] → The swarm rule (build the next package after the agent returned) prevents it; a violation shows as a report stored under the wrong role, which the content of the report makes visible.
- [Machine-only evidence cannot be re-checked on another clone] → Only binaries and large files; the manifest keeps their hashes, and committed reports carry the citations.
- [Kind count and the `post-task-step` prompt key change] → `pipeline/post-task-step.md` was a placeholder no project overrides; a project file at that path now answers `policy/unknown-config-key`, which names it.

## Migration Plan

No release shipped the evidence commands, the step kinds or the `post-task-steps` action, so no project data migrates. `next.action: post-task-steps` becomes `commit` in the `attempt close` schema (contract only). The `pipeline/post-task-step.md` default is replaced by three files. Rollback is a revert of the PR.
