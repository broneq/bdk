# Design

## Context

See proposal.md, Why. Four decisions were taken by the user on 2026-09-28 before the proposal (T30-D0 to D3 below). Decision ids continue as `T30-Dn`.

State today:

- `spec delta check`, `spec merge`, `spec diff` and `change close` exist as index records, specs and output schemas, but have no handler: they answer `kernel/not-implemented`. There is no `kernel/src/spec/`.
- The `spec-delta` kind (`graph/domain/kinds/documents.ts`) lists only top-level `spec-delta/*.md` and checks that they exist and are not blank. The layout pattern (`shared/store/state/registry.ts`) accepts `spec-delta/<slug>.md`, flat, while the plan part schema (`shared/store/state/plan.ts`) allows capability names with `/` and the plan part check (`graph/domain/kinds/parts.ts`) looks for `spec-delta/${capability}.md`: a nested capability can never pass today.
- `spec-impact` is a required plan part field.
- `shared/store` holds the prune function (`prune.ts`) that `change close` must call, `findChange` already looks for `.bdk/changes/archive/<id>/`, the `Store` has no rename of a directory, and `pathspecCommit` (`shared/git`) commits named paths only.
- `doctor` (`service/use-cases/doctor.ts`) has no spec check; its record declares `policy/merge-hash-mismatch`, which a command that exits 0 with findings cannot emit.
- `archive.keep-evidence`, `spec.normative-word` and `policy.checkpoint.squash-at-close` are planned keys owned by T30 (`shared/config/known.ts`).
- `openspec` 1.13.2 accepts a main spec with YAML frontmatter (checked by hand in the scratchpad: `openspec validate --specs --strict` on a file with `bdk-merge-hash` frontmatter passes) and itself refuses a MODIFIED block that drops a scenario, which is the same semantics as `scenario-lost`.

## Goals / Non-Goals

**Goals:**

- A delta that would silently lose behaviour never reaches `.bdk/specs/`: scenario loss, a missing WHEN or THEN and a missing normative word are refused at plan time (part check), at `done spec-delta` and at merge.
- The merge is a pure function of the deltas and the current spec files, so it is idempotent and reviewable through `spec diff`.
- Parallel Changes that change the same requirement are stopped with both texts, and only then is the model asked.
- A Change can be closed end to end: merge, prune, archive, commit.

**Non-Goals:**

- The `PreToolUse` guard on `.bdk/specs/` (T24); learning routing and the rule projection (T31); the `close` stage skill (T41); migrating BDK's own `openspec/specs/` (T50).
- RENAMED requirements: OpenSpec has them, the plan's scope names ADDED / MODIFIED / REMOVED only; a rename is REMOVED plus ADDED.

## Decisions

- **T30-D0 One Change for all of T30 (user choice).** Spec slice, validators, doctor and `change close` ship together, because `close` is the only real consumer of the merge and the acceptance scenarios cross both. Alternative: part A spec slice, part B close - rejected by the user; two verification rounds for one contract.
- **T30-D1 Conflicts per Requirement against archived Changes, resolved by a `decision` (user choice).** A requirement of capability `C` conflicts when an archived Change `Y` whose `close` transition is later than this Change's creation named it in `spec-delta/C.md` with a different block text, and no `decision` entry of this Change has `refs` naming `Y` and `spec-delta/C.md`. `ours` / `theirs` are the two delta blocks, so the output "shows both deltas" (risk "Spec merge conflicts"). The archive keeps `spec-delta/` (the prune touches only `dispatch/` and `reports/`), so `theirs` is always readable. The ledger entry makes the resolution part of the Change's history, which the PR summary shows. Alternatives: a base hash stamped into the delta - rejected by the user, it needs a kernel-stamping command and makes the delta no longer plain OpenSpec; every earlier Change touching the capability - rejected, independent requirements of one capability would always conflict.
- **T30-D2 A scenario is removed only by listing it under REMOVED (user choice).** In `## REMOVED Requirements`, `### Requirement: X` followed by `#### Scenario: Y` lines removes only those scenarios; the heading alone removes the requirement. A MODIFIED block that drops a scenario without that listing is `scenario-lost`. This keeps the delta valid OpenSpec (REMOVED items carry free text) and makes every loss explicit (C1-C3). Alternative: only whole-requirement removal - rejected by the user, it forces a rename to drop one scenario.
- **T30-D3 No squash at close (user choice).** `--squash`, `squashed` and `policy.checkpoint.squash-at-close` leave contract 3 (removing a flag is allowed in the implementing PR, `kernel-cli` Amendment rule; the key was planned, never registered). Rewriting history would change the commits that trailers (`BDK-Part`, `BDK-Task`) and attempt records name, and `rebuild` would then find a trailer mismatch. A squash merge of the PR gives the same short history. Alternative: rebase with fixup - rejected by the user.
- **T30-D4 Nested delta paths.** The delta of capability `auth/login` is `spec-delta/auth/login.md`, mirroring `.bdk/specs/auth/login/spec.md`. The contract example's `spec-delta/auth-login.md` was ambiguous (a hyphen is legal inside a segment, so `auth-login` could be one segment). The layout pattern becomes the capability grammar of the plan part schema; the kind lists `spec-delta/` recursively. Alternative: a flat slug with `--` as separator - rejected, a second naming rule for the same name.
- **T30-D5 Merge algorithm.** Requirements are matched by trimmed, case-sensitive name. REMOVED first, then MODIFIED in place, then ADDED appended in delta order, then the purpose; the result is rendered canonically (title, Purpose, Requirements, blocks separated by one blank line, LF, trimmed trailing whitespace). Canonical rendering is what makes idempotence a byte equality and makes the file OpenSpec's main format. Idempotence without stored base: an operation the file already shows as merged by this Change is a no-op (ADDED or MODIFIED block equal; a removal absent from a file whose `bdk-change` is this Change); the delta check uses the same rule, so it still passes after a merge. An ADDED requirement present with another text in a file last merged by this Change is replaced (the delta was edited after a first merge); otherwise it is `requirement-exists`. Alternatives: merge by position - rejected, positions shift with every Change; keeping the pre-merge base in `.machine/` - rejected, lost on a fresh clone.
- **T30-D6 Merge hash over the body, two frontmatter keys.** `bdk-merge-hash: sha256:<hex>` of the UTF-8 body after the frontmatter, and `bdk-change: <id>`. The hash does not cover `bdk-change`, so the key can serve idempotence without a second hash; a hand edit of the key alone is harmless (the next merge by another Change overwrites it). A file without the key is a mismatch, so a hand-created spec is refused until it comes through a delta. Alternatives: hash of the whole file - rejected, the hash would have to exclude itself; a sidecar hash file - rejected, two files to keep in step and a second path the guard must cover.
- **T30-D7 `spec merge` without `--dry-run` requires `gate:review`.** The living spec records reviewed behaviour only; `--dry-run` and `spec diff` preview at any time. `close` runs the same merge, so a standalone merge is a way to resolve conflicts before `close`, never a way around review. Alternative: merge at any time - rejected, `.bdk/specs/` would hold unreviewed behaviour that another branch might pick up.
- **T30-D8 `spec delta check` refuses with the full problem list in `why`.** The error object has exactly four fields (`kernel-cli`), so a failing check exits 2 with `policy/spec-invalid` and `why` listing `<path>:<line> <code>: <message>` joined by `; `; `bdk validate spec-delta --json` gives the structured list with exit 0. The contract example with `valid: false` and exit 0 contradicted its own `policy/spec-invalid` scenario; the example now shows a passing check. New problem codes join the output enum: `scenario-missing`, `requirement-exists`, `requirement-duplicate`, `section-unknown`, `purpose-missing`, `delta-empty`.
- **T30-D9 Validators call `spec` through a `graph -> spec` edge.** The graph's view (`graph/use-cases/view.ts`) asks `spec`'s check for the problems of each delta, reading the delta and the current spec through `shared/store`; the kinds stay pure and read `view.specDelta(capability)`. The `spec-delta` kind's check `delta:<capability>` carries `policy/spec-invalid` (declared by `validate`); the plan part's `spec-impact` check carries no rule of its own (`policy/validation-failed`), because `part start` does not declare `policy/spec-invalid` and a part check is about the plan, not the delta's grammar. `spec` stays a leaf. Alternative: the parser in `shared/` - rejected by the admission rule, only `spec` and `graph` use it (`change` reaches it through `spec`).
- **T30-D10 `spec-impact` optional, default by profile.** The field becomes optional in the plan part schema; absent is `none` for `tiny` and `small` and fails the `spec-impact` check for `large` ("declare spec-impact: none or the capabilities"). This is the plan's "a spec delta is optional for the `tiny` and `small` profiles (`spec-impact: none` is the default there)". Alternative: keep it required everywhere - rejected, it contradicts the plan; default `none` everywhere - rejected, a large Change would skip the spec by omission.
- **T30-D11 `change close` order and atomicity.** All checks run before the first write (gate, tickets, trailers, git state, then the merge's checks). The writes are merge, `close` transition in the Change's `log/`, prune, move, marker removal, one pathspec commit of `.bdk/specs/`, `.bdk/changes/<id>/` and `.bdk/changes/archive/<id>/` with `BDK-Change: <id>`. A failing git hook leaves the result in the work tree and answers `policy/git-hook-failed`; a rerun finds no active Change, so the user commits by hand, which the `instead` says. The archive is `.bdk/changes/archive/<id>/` because `findChange` and the index already use it and the id already starts with the date; the contract's `<date>-<id>` is corrected. A `move` primitive joins `Store` (rename on disk; the memory store moves every key under the prefix), since `node:fs` is allowed only in `shared/store`. Alternatives: copy and delete - rejected, not atomic on one file system; commit through `commit` - rejected, `commit` is the task commit with part and task trailers.
- **T30-D12 Close output until T31.** `learning.proposedRules`, `learning.spec` and `learning.nothing` are empty lists and `.claude/rules/bdk-generated.md` is not written; T31 adds `log route` and `rules export` to `close`. The PR summary is built from the ledger alone (intent, live decisions, assumptions and risks, open findings and blockers, merged capabilities), so it does not depend on T31.
- **T30-D13 `doctor` reports, never refuses.** One `merge-hash` finding with level `fail` per mismatching file; `policy/merge-hash-mismatch` leaves the doctor record, whose exits become `0, 3, 5`. The repair is a single command restoring the file from the last close commit that touched it.
- **T30-D14 OpenSpec compatibility test.** A contract test builds a fixture Change, merges it through `dist/bdk.mjs`, copies `.bdk/specs/` into `openspec/specs/` of a temporary repository and runs `openspec validate --specs --strict --json`. CI installs `@fission-ai/openspec@1.13.2` (the version `CLAUDE.md` pins); locally the test is skipped with a message when `openspec` is not on `PATH`, and it fails in CI when it is missing (`CI` set), so it cannot pass vacuously there. BDK does not depend on OpenSpec at runtime (T02 decision Q-1).
- **T30-D15 BDK's own spec stays in `openspec/`.** Whether `openspec/specs/` migrates into `.bdk/specs/` is T50's question (plan, note on the seam); T30 only proves the format is compatible.
- **T30-D16 The review gate reaches `spec` through the composition root.** `spec` is a leaf, yet `spec merge` needs `gate:review` done (D7). `SpecDeps` takes a `reviewGate` function, which `registrations.ts` binds to `graph`'s `requireGate`; `graph/use-cases/gate.ts` exposes `gateRefusal` (on an open index) and `requireGate` (opening it). `change close` may import `graph` and calls `gateRefusal` directly. Alternative: `spec` imports `graph` - rejected, `graph` already imports `spec` for the delta validators, so the edge would make a cycle.

## Risks / Trade-offs

- [Clock skew between machines makes "closed after created" wrong] -> both timestamps are kernel clock values from different machines; a false conflict costs one `decision` entry, a missed one is still caught by git's own textual conflict on `.bdk/specs/<capability>/spec.md` and then by the hash check. Accepted.
- [Canonical rendering reformats a spec imported by hand] -> such a file has no merge hash and is refused first; it enters only through a delta or T32's import, which writes the canonical form.
- [A delta edited after a standalone merge] -> covered by T30-D5's replace rule for blocks this Change merged; a removal edited back into a modification of an already removed requirement is `requirement-unknown`, and the fix is to ADD it again.
- [`openspec` changes its strict rules] -> the CI version is pinned; bumping it is a deliberate PR that reruns the contract test.
- [The close commit fails on a hook after the move] -> the state is consistent on disk (archive complete, index refreshed); only the commit is missing, and the refusal says which paths to commit.
