# Design

## Context

`bdk plan check` (spec `bdk-cli/plan`) reports problems of eleven kinds, listed in order as `CHECKS` in `plugins/bdk/src/plan/domain/check.ts`. The Reference (spec `docs-site`, design of v3-268-docs-site-user-docs D1, D3, D4) is generated by `pnpm docs:reference` from a source model (`scripts/docs-reference/model.ts`) that already imports domain code of the `bdk` plugin (`describeSettings`, `parseRule`). Hand-written pages are checked by name only (`pnpm check`, "Hand-written pages name only what exists"), so a fix text copied into Concepts would drift unseen.

## Decisions

### D1: The problem texts live beside `CHECKS` in the plan domain

`check.ts` exports `PROBLEMS: Readonly<Record<Check, { meaning: string; fix: string }>>`. The record type makes a check without its text a type error, so `pnpm check` (typecheck) fails before any test runs; a unit test also compares the keys with `CHECKS`. The CLI keeps reading `CHECKS` from the same module, so the kinds it reports and the kinds the Reference lists are one list.

Alternatives:
- A Markdown table under `docs/` that a test compares with `CHECKS`: the text then lives away from the code that decides the problem, and a contributor who changes a check's meaning edits two places. Lost on maintainability.
- Fix text on the command declaration (`Command`) rendered by `--help`: needs a new generic field in the CLI frame for one command, and puts long prose into fixed-width help text where it reads badly. Lost on simplicity.
- Printing the fix with each problem in the `bdk plan check` output: changes the model-facing output that `plan-draft` and `plan` read, which needs eval evidence (CLAUDE.md, "Building skills"); none shows a problem today. Out of scope, recorded as a possible follow-up.

### D2: A section of the CLI Reference page, not a new page

The problems render as `#### Problems {#plan-check-problems}` right under the `bdk plan check` entry of `docs/reference/bdk/cli.md`: a table with the problem kind, what it means and what to do, in `CHECKS` order (the order the check lists them). A reader who searches for the command finds its problems beside its help, and the sidebar needs no new entry.

Alternatives:
- A page `docs/reference/bdk/plan-check.md`: one more page and sidebar entry for one table, separated from the command it explains. Lost on simplicity.
- One heading per kind: eleven `####` headings swell the page outline; the table is shorter and the kinds are short words a reader can scan. Lost on readability.

The renderer adds the section through a small map from a command path to its extra sections, so the generic CLI rendering stays one loop.

### D3: Concepts explain the model, not the planner's rules

The new section of `docs/concepts/stages.md` says what a part, `depends-on`, a wave and `isolation` mean for the user, how waves follow from `depends-on` (a part with no dependency is in wave 1; any other part is one wave after its latest dependency), that the planner aims at the fewest waves, and what to look at when reviewing a part file. It does not copy the cutting rules of `plan-draft`, which change with its evals (issue scope). Every problem detail is a link to the Reference table.

## Risks / Trade-offs

- The Concepts prose names facts the code decides (wave rule, `isolation` values). They are stable contracts of spec `bdk-cli/plan`; a change there is a spec change that names its docs.
