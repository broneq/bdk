# Proposal: v3-t31-rules-ids-funnel

## Why

Plan: docs/V3-IMPLEMENTATION-PLAN.md, T31. Tracks #58 (https://github.com/broneq/bdk/issues/58).

BDK's quality rules are 131 unnumbered bullets in nine files, and every role receives whole categories whatever files a task touches. No report can say which rule forced a decision, nothing tells a useful rule from one the model already knows, and v2's only ways to grow the rules (`add-rule` from a single incident, the drift hook) wrote rules without evidence. T40 has now measured every bullet (`docs/V3-EVAL-RULES-NOOP.md`), so the data to prune before numbering exists (T5).

Input carried over by citation: design "Rules with IDs (R-rule-id, S4)" and "Measure before numbering (T5)", P7, D2a, risk "Measurement delays the rule migration", T02 decisions Q-4, Q-5, Q-6 and R-3 with the round 3b analysis (`docs/V3-SKILL-INVENTORY.md`), `skills/refine-rules/references/rule-admission.md`, and the T40 hand-off.

User decisions taken while proposing (2026-09-30), which narrow the plan's scope:

- **What a rule is.** A rule is a choice among valid alternatives that the project (or BDK) made and wants followed ("we use CQRS"). A fact about the system ("users and permissions are joined by `user_id`") is not a rule; it belongs in code, docs or a spec. A process lesson ("the negative test was forgotten") is not a rule either; it is a signal about how the work went.
- **Route B: core now, minimal funnel.** Clean-up, IDs and selection land now. The learning funnel shrinks to collection plus an audit view: nothing is proposed at `close` or during a task, there are no `rules.propose-when.*` thresholds with an authors count, and no T5 rerun of a failed attempt. Adoption happens in a separate, manually started audit session that reads the kernel's audit view, groups recurring items by meaning, and proposes both project rules (the user accepts each one) and improvements to BDK itself. The audit skill belongs to T42; T31 builds its kernel side.
- **Recurrence threshold:** an item is recurring when it appears in at least 3 distinct Changes (a loop repeating one mistake inside one Change counts once).
- **Capturing a lesson** uses the existing `bdk log add learning`; `rules add` is dropped because its name promised a rule. A rule is written only by `bdk rules accept`, the user's explicit adoption.
- **Pruning the shipped pack:** remove the 44 bullets measured as no-ops in both M1 and M2 (after the spot-check corrections); a bullet whose content is a fact (`kind: knowledge`) stays only when M1 shows a model not knowing it (WRONG, MISSED or MIXED for Haiku or Sonnet); fix the seeds of the 14 bullets no cell detected and re-measure them before deciding.
- **The BDK pack is read live from the plugin bundle** as `BDK-*` ids and switched off per id with `rules.disabled`; `setup` copies nothing.

## What Changes

- **Rule definition and admission.** The definition above becomes the authoring convention (`.claude/rules/quality-rules.md`, the user guide) and the content test for the shipped pack: every rule is `kind: house` (a choice) or `kind: knowledge` (a fact that corrects the model, with `source` and `verified`). The measurement procedure is mandatory for every new `rules/languages/` file.
- **Pack migration.** A decision report `docs/V3-RULES-MIGRATION.md` holds one row per T40 bullet (class, kind, decision, new id or removal reason). The surviving bullets become one file per rule under `rules/<category>/` and `rules/languages/<name>/` with `BDK-<PREFIX>-n` ids (`CQ`, `ARCH`, `DP`, `SEC`, `TQ`, `EJ`, `PL`, `JS`, `TS`, `REACT`); removed bullets get no number. `rules/plan.md` content arrives as `BDK-PL-1..3` (P7).
- **Rule store and selection in the kernel.** Rules load from the bundle and from `.bdk/rules/`; selection per ticket intersects `applies` with the target's files, filters by role, `languages` and `rules.disabled`, orders global first, then by glob specificity, then `since`, and selects every applying rule: there is no cap, and `hooks session-start` warns when a role would read more than `rules.warn-above` rules. The dispatch package records the selected ids; `rules show --ticket` prints exactly those rules with their ids. `ctx` renders rules with their ids.
- **Commands.** `rules check`, `rules show <id>` (tombstones included), `rules explain <file>`, `rules prune`, `rules import` (a target project's `.claude/rules/*.md`: prefix from the file name, one rule per top-level bullet, `applies` from `paths:`, global when `paths:` is absent), `rules export --claude` (project rules only, regenerated by `accept` and `import`), `rules stats` as the audit view (recurring fingerprints across at least `rules.audit.min-changes` Changes, the raw `finding` and `learning` entries of every Change including the archive for grouping by meaning, citations by rule id), and the new `rules accept`. `log add learning` gains `--applies`.
- **Citations.** Role contracts require the implementer and the reviewing roles to cite the id of every rule that forced a decision, as a `--ref` of the entry or in the report; `rules stats` and `rules prune` count those refs.
- **BREAKING (unreleased contract):** `rules add` and `log route` are removed; `change close` no longer routes learnings or writes the rule projection, and its `learning` output field goes; the `routed` status and `routed-to` field of ledger entries go; the settings `rules.propose-when.*` and `rules.max-learnings-per-change` go, `rules.audit.min-changes` (3) and `rules.prune.uncited-changes` (20) arrive; the prompt keys `rules/<category>` and `rules/languages/*` go (a project adds its own rule files and disables BDK ones by id instead).
- `doctor` warns about a hand-written `.claude/rules/*.md` rule file that carries no id (T02 decision Q-6).

Out of scope: the audit skill and the `rules` skill replacing `add-rule` and `refine-rules` (T42); `setup` and `close` skill changes (T41); deleting the v2 skills' Python scripts (T32); `cr` consuming the package (T42); cross-project aggregation (Q-4, left open).

## Capabilities

### New Capabilities

- `rule-pack`: what a rule is, the shipped `BDK-*` pack's layout and content test, the measurement procedure for new language files, the plan rules `PL`, and the migration report.

### Modified Capabilities

- `kernel-cli`: the error codes that `rules accept` and `rules export` raise, and the availability classes without `log route` and `rules add`.
- `kernel-cli/rules`: `check`, `show <id>`, `show --ticket` by id and `applies`, `explain`, `prune`, `import`, `export`, `stats` as the audit view; `accept` added; `add` removed.
- `kernel-cli/log`: `log add learning --applies`; `log route` removed; `routed` no longer settable.
- `kernel-cli/change`: `change close` no longer routes learnings or writes the projection.
- `kernel-cli/hooks`: `hooks session-start` warns when a role reads more rules than `rules.warn-above`; no package drops rules.
- `kernel-cli/ctx`: the `rules` and `language-rules` parts render rules by id from the rule store.
- `kernel-cli/dispatch`: the package stamps every selected rule id (no cap), and `template-hash` covers the selected rule texts.
- `kernel-cli/service`: `doctor` warns about rule files without an id.
- `kernel-state`: rule frontmatter (`origin` values, `evidence`, bundle ids), the dispatch package's `rules`, the `learning` type without `routed-to`, status without `routed`, and the write map.
- `kernel-settings`: the `rules.*` key table and the removed `rules/*` prompt keys.
- `kernel-architecture`: the `log` and `rules` rows of the slice table.
- `role-contracts`: rule ids cited by the implementer and the reviewing roles.
- `kernel-pipeline`: a node's `rules` names categories of the BDK pack instead of rule prompt keys.
- `skill-evals`: the `rules-noop` suite reads the per-rule pack and takes a `--patches` filter.

## Impact

- Kernel: `kernel/src/rules/` (store, selection, eight commands), `kernel/src/dispatch/use-cases/build.ts`, `kernel/src/ctx/`, `kernel/src/log/` (route, `--applies`), `kernel/src/change/` (close, status), `kernel/src/service/` (doctor), `kernel/src/shared/config/known.ts`; `schema/cli/` and `schema/state/` regenerated; `dist/bdk.mjs` rebuilt.
- Content: `rules/` restructured into per-rule files; `skills/roles/*/SKILL.md` citation lines; `.claude/rules/quality-rules.md`; `docs/guide/` pages about rules; `evals/suites/rules-noop/violations.yaml` seeds for 14 bullets.
- Measurement: one targeted M2 re-run through the T40 harness; its projection is approved by the user before the full series runs.
- Documents: `docs/V3-RULES-MIGRATION.md`; the T31 resolution in `docs/V3-IMPLEMENTATION-PLAN.md`.
