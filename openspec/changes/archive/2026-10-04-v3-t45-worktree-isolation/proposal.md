## Why

Scope: #107 (https://github.com/broneq/bdk/issues/107). Tracks #107. Depends on T41.

T41 runs independent plan parts in parallel in one working tree and keeps parts with overlapping `Files:` apart (T41-D13, user decision 2026-10-02). What `Files:` cannot see is still shared: a lockfile or codegen output both parts regenerate, migration numbering, snapshot files, a whole-project build or typecheck that sees the other part's half-done code, tests sharing a port, a database or fixtures. The user decided this is a judgment call of the planner, not one fixed mode. This Change lets the planner give a part its own git worktree. The kernel then creates the worktree, runs the part's commands there, merges the part back and cleans up, so agents never negotiate shared state with each other.

## What Changes

- **Plan part field** `isolation: shared | worktree` (default `shared`) and `isolation-reason`, a one-line reason that `worktree` requires. A new plan rule `BDK-PL-4` tells `/bdk:plan` to choose `worktree` only when the reason names shared state outside `Files:`. A new plan part check `isolation` refuses `worktree` without a reason.
- **Verifier**: the `verifier` contract gains an isolation check. A `shared` part in one wave with another part where both touch hidden shared state is a blocker of category `integration-failure`. A `worktree` part whose reason names no state outside `Files:` is a finding.
- **Kernel-owned worktree.** `bdk part start` of a `worktree` part runs `git worktree add` on a new part branch from the Change branch's `HEAD`, never from the default branch. It copies the gitignored files that `.worktreeinclude` lists and runs the configured setup command with a time bound. The command, exit code, duration and output tail go into the start marker entry. A failed setup refuses (`runtime/worktree-setup-failed`) and leaves no worktree behind.
- **One ledger, one home checkout.** A kernel command run inside a part worktree resolves the project root and the Change state from the home checkout. Part branches never carry `.bdk/` changes. Every command that reads or writes the work of a task or part (`commit`, `attempt close`, the diff check, `evidence record` and `evidence check`, the tree hash) uses that part's **work root**: its worktree while the part is live, the home checkout otherwise.
- **Merge back at `bdk part done`.** `git merge-tree --write-tree` first checks for a conflict without touching any working tree. On a clean result `git commit-tree` writes a merge commit with the `BDK-Change` and `BDK-Part` trailers, and the commit lock then moves the Change branch forward with `git merge --ff-only` in the home checkout. The commits of the part keep their SHAs and trailers. A conflict refuses with `policy/merge-conflict` and sends the part to a merge ticket (`bdk attempt open verify-fix <part>`). The kernel starts the merge inside the worktree, the implementer resolves only the conflicted paths under the project's merge instruction, the ticket's steps verify the merged state, and the kernel commits the merge. An exhausted budget parks the Change for the user. A dirty home path that the merge would overwrite refuses with `policy/merge-blocked` and asks for a retry after the shared task commits.
- **Merge instruction** `fragments/merge-conflicts`, a prompt value the project extends. The BDK default holds the rules common to every language: a package manager's lockfile is never merged by hand, it is regenerated from the merged manifests; other generated files are regenerated by their command; colliding migrations are renumbered; source code keeps the intent of both sides. The instruction is general, so any merge, also of the default branch, can follow it.
- **Rule `BDK-CQ-9`**: a package manager's lockfile is regenerated, never merged or edited by hand. `applies` scopes it to lockfile globs, so it reaches every package that touches a lockfile, a merge of `main` resolved by an implementer included. It is admitted without the M1/M2 measurement as the second exception after the `SEC` rules (user decision 2026-10-04).
- **Cleanup and recovery.** After the merge the kernel removes the worktree and its branch. Before removal it records leftover undeclared files as one kernel `finding`. `bdk rebuild` removes worktrees of done or never-started parts, keeps the worktree of a live part, recreates a missing one from its branch, and reports each one in `worktrees`.
- **`bdk next` wave items** carry `isolation` and, for a live worktree part, `workdir`. When worktrees are disabled, a `worktree` part runs alone. When `execution.worktree.max-live` worktrees exist, a `worktree` part waits for a later wave.
- **Dispatch**: the package of a worktree part carries `workdir` in its frontmatter and a `Work root` body section. `/bdk:execute`, the lead and the role contracts work there. A new pre-tool guard `guard/worktree-scope` denies a subagent's `Edit`, `Write` or `NotebookEdit` outside its package's `workdir`.
- **Settings** `execution.worktree`: `enabled`, `dir`, `setup.command`, `setup.timeout`, `max-live`. Gitignored files come from `.worktreeinclude`, the file Claude Code reads too, so the kernel adds no list key for them.
- **Hosts**: `skills/swarm/references/hosts/claude-code.md` notes that the Agent tool has no working-directory parameter and that the plugin `settings.json` cannot set `worktree.baseRef`. Only `agent` and `subagentStatusLine` take effect there, per https://code.claude.com/docs/en/plugins-reference, Fields, `settings`. BDK therefore never uses `isolation: worktree` on its adapters.

## Capabilities

### New Capabilities

None. Every behaviour lands in an existing kernel or skill spec.

### Modified Capabilities

- `kernel-state`: plan part fields `isolation` and `isolation-reason`; attempt record fields `merge` and `conflicts`; dispatch package field `workdir`; new requirement "Part worktree", covering the location, the branch, the home marker and the work root.
- `kernel-loops`: plan part check `isolation`; diff check and progress from git per work root; the part merge commit in the trailer rules.
- `kernel-settings`: module `execution.worktree` and its keys; prompt key `fragments/merge-conflicts`.
- `kernel-cli/part`: `part start` creates and sets up the worktree; `part done` merges back and cleans up; new rules `runtime/worktree-setup-failed`, `policy/merge-conflict`, `policy/merge-blocked`, `policy/worktree-dirty`.
- `kernel-cli/graph`: `bdk next` wave items carry `isolation` and `workdir` and apply the disabled and `max-live` rules.
- `kernel-cli`: project root resolution from inside a kernel worktree.
- `kernel-cli/service`: `bdk rebuild` recovers worktrees.
- `kernel-cli/dispatch`: `dispatch build` writes `workdir`, the `Work root` section and, for a merge ticket, the `Conflict` section.
- `kernel-cli/attempt`: `attempt open verify-fix` of a conflicting worktree part opens a merge ticket; `attempt close` checks the resolution and commits the merge (`policy/merge-unresolved`).
- `kernel-cli/hooks`: guard `guard/worktree-scope`.
- `role-contracts`: the verifier's isolation check; contracts that work in `workdir`.
- `stage-skills`: `/bdk:plan` writes the isolation fields; `/bdk:execute` handles the worktree refusals.
- `rule-pack`: rules `BDK-PL-4` and `BDK-CQ-9`; the admission exception for `BDK-CQ-9`.
- `docs-site`: the new page `concepts/worktree-parts.md`, written for v3, carries no v2 banner.
- `kernel-architecture`: `shared/git` holds the part worktree operations and the bounded setup run; `service` settles part worktrees through `part`.

## Impact

- Kernel: `kernel/src/shared/git/worktree.ts` (new: add, merge-tree, commit-tree, fast-forward, remove, setup run), `kernel/src/shared/store/` (plan part schema, `findProjectRoot`, home marker, work root), `kernel/src/part/` (start, done, diff, merge ticket, rebuild recovery), `kernel/src/attempt/` (merge ticket), `kernel/src/commit/`, `kernel/src/evidence/use-cases/scope.ts`, `kernel/src/graph/domain/wave.ts`, `kernel/src/dispatch/`, `kernel/src/hooks/` (guard), `kernel/src/service/` (rebuild), `schema/cli/` (regenerated).
- Content: `skills/stages/{plan,execute}/SKILL.md`, `skills/roles/{verifier,lead,implementer,runner}/SKILL.md`, `skills/swarm/`, `rules/plan/BDK-PL-4.md`, `rules/code-quality/BDK-CQ-9.md`, `fragments/merge-conflicts.md`, user docs (`docs/guide/`) for the setting and the plan field.
- Git: requires `git merge-tree --write-tree` (git 2.38 or later); `part start` of a worktree part refuses an older git with `runtime/git-too-old`.
- Out of scope: overlapping `Files:` stay sequential (T41-D13), a worktree does not replace that. A kernel-run regeneration of conflicted files is out of scope too (Decision 5). A kernel command that merges the default branch into a Change is not needed: evidence freshness already follows file content, and a merge of `main` carries no BDK trailers (user decision 2026-10-04). The `execute` stage probe on the fixture is run here, and the full acceptance E2E belongs to T50. Non-git version control is not supported.

## Decisions

Resolved from the "To resolve in the spec" list of #107 and the user's answers of 2026-10-04. design.md gives the rationale.

1. **Per part, not per wave.** The planner decides each part. `/bdk:execute` never downgrades a part. The only downgrade is the deterministic `execution.worktree.enabled: false`, under which a `worktree` part runs alone in the shared tree. A failed setup refuses to the user (user decision 2026-10-04).
2. **Setup in settings.** The setup lives in `execution.worktree.setup` (`command`, `timeout`). The time bound is `setup.timeout`, 10 to 540 s with a default of 300, which keeps a `part start` inside the host's 600 s Bash limit. The disk bound is `max-live`, the number of worktrees alive at once. The location is `execution.worktree.dir`, default `.bdk/.machine/worktrees` (user decision 2026-10-04).
3. **Merge commit, not rebase** (user decision 2026-10-04). The part's commits keep their SHAs and trailers. A content tree hash depends only on file bytes, so evidence recorded in the worktree stays fresh after the merge exactly when the covered files are equal. A lockfile changed on both sides makes evidence stale, which is the intended result.
4. **One ledger** (user decision 2026-10-04, supersedes "ledger entries merged" in the issue's Scope). State lives only in the home checkout, so nothing is merged and there is no ledger conflict.
5. **Conflicts go to a merge ticket, not straight to the user** (user decision 2026-10-04). This narrows the issue's acceptance wording "no agent is asked to resolve a conflict" to "no agent resolves a conflict freely": the agent works inside a budgeted `verify-fix` ticket, on the named paths, under `fragments/merge-conflicts`, and the ticket's steps verify the result. The `regenerate` settings list was considered and dropped (design D6).
