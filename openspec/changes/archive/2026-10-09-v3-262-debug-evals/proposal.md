## Why

Tracks #262.

Two scenarios of `openspec/specs/bdk-debug/spec.md` have no eval case: "Fix too large for one part" and "Resume after the fix" (`openspec/changes/archive/2026-10-08-v3-204-bdk-debug/design.md`, "Measurements": "Not covered by an eval case"). A path without a case can break unnoticed. The same "Measurements" record one `debug-fix` run at 0.91 whose `test-red-then-green` grader did not match, with the workspace gone before the cause could be read, so the acceptance signal of `/bdk:debug` rests on a miss nobody understands.

## What Changes

- New orchestrator eval case `debug-too-large`: the tally crash with `plan.part.max-files: 1`, so the fix (code and test) does not fit one part; graded that `diagnose-bug` writes the proposal and `design.md` but no plan part, `debug/diagnosis.md` reads `Status: too-large` with `Next: /bdk:design fix-total-crash`, and `/bdk:debug` stops without a gate, a commit, `execute` or `auto-review`.
- New orchestrator eval case `debug-resume-review`: the recorded `debug-fix` run of the `diagnose-run.sh` fixture cut back to the end of `execute` (diagnosis, auto gate, the committed Change and fix, `execute/result.md` `Status: done`, no review); graded that `/bdk:debug fix-total-crash` starts at `auto-review`, runs neither `diagnose-bug` nor `execute`, and writes `debug/result.md`.
- `debug-fix` rerun with kept workspaces: the miss is an implementer that read only the 20-line tail `bdk check run` prints under a red check, did not see its reproduction test fail there, never opened the output file, and hedged the report line (design.md, "What the rerun showed"). Fixed where it starts:
  - `bdk check run` prints, under a red check whose tail is 20 lines, that these are the last 20 lines and the whole output is in the file (D3).
  - `implement-part` finds each acceptance test's own failure in the output file and writes each acceptance line in one form, `; red seen; green seen` (D4).
  - `diagnose-bug` makes the reproduction the part's only acceptance scenario and adds no task that only pins behaviour that already works (a second way to the same miss, D9).
  - The graders `debug-fix/test-red-then-green` and `implement-part-csv/red-then-green` require that form on every acceptance line (D5).
- `/bdk:debug` goes on after a block's own reply in the same turn (two runs ended after `diagnose-bug`'s reply, D6), and its description routes a reported symptom to it also when the fix turns out to be one line (two runs edited the code directly, D7). Both blocked the acceptance signal of #262.
- `plugins/bdk/evals/README.md` names the two new cases and the measured scores.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `bdk-debug`: "Fix Change" says the reproduction is the part's only acceptance scenario; "Skills" says that a block's reply does not end the run and that a reported symptom routes to `/bdk:debug`; "Eval cases of debug" adds the cases `debug-too-large` and `debug-resume-review`, each tied to the scenario it covers.
- `bdk-cli/check`: "Check run text output" adds the note under a cut tail.
- `bdk-execute`: the implementer reads each acceptance test's failure in the output file and writes the acceptance line in one form.
