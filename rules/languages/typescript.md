# TypeScript — Language Rules (2026)

Principles for TypeScript 5.x / 7.x (native compiler) codebases. Applied during planning, implementation, and review when `typescript` is in `.bdk/settings.json` `languages`. These layer on top of the plain JavaScript rules — everything true of JS is still true here.

- **Strict mode is the floor, not a goal.** Run with `strict: true` from the first commit; retrofitting it onto an existing codebase is far more painful than starting strict. Treat any project without it as a finding, not a preference.
- **Turn on the checks `strict` leaves out.** `noUncheckedIndexedAccess` (index access yields `T | undefined`) and `exactOptionalPropertyTypes` (optional ≠ implicitly `undefined`) catch a whole class of null/optional bugs that the `strict` bundle alone misses. Enable both in production code.
- **`unknown`, never `any`, at the edges.** `any` switches off the type checker and lets unsafe values flow silently through the program; `unknown` forces an explicit narrow before use. Use it for parsed JSON, API responses, and external input — `any` is a finding unless justified with a comment.
- **Annotate the boundaries; infer the interior.** Declare parameter and return types on exported functions, public class members, and module APIs — they are the contract. Let inference handle local variables and implementation detail, where annotations are just noise that drifts.
- **Types vanish at runtime — validate untrusted input with a real parser.** A type annotation is erased before the code runs and guarantees nothing about the value that actually arrives. Parse every trust-boundary input (request bodies, env vars, DB rows, message payloads) through a runtime schema (Zod, Valibot, ArkType) and follow *parse, don't validate*: return a typed value that proves validation happened.
- **Model variants as discriminated unions.** Give each variant a shared literal tag (`type`/`kind`/`status`) so control-flow narrowing resolves the union precisely and exhaustiveness checks catch the missing case. Prefer this over inheritance or a bag of optional fields for any closed set of states.
- **Make illegal states unrepresentable.** Brand semantically distinct primitives (`UserId` vs `OrderId` vs raw `string`), collapse mutually-exclusive booleans into a single discriminant, and shape types so the compiler rejects the impossible combination instead of leaving it to a runtime guard.
- **Guard exhaustiveness with `never`, preferably via a reusable `assertNever` helper.** In the default branch of a switch (or the final `else`) over a closed union, route the discriminant through `assertNever(value: never): never` rather than a bare runtime throw. When someone later adds a union member, the new type is no longer assignable to `never`, so the compiler fails the build — a compile-time guarantee strictly stronger than a runtime throw that only fires once the unhandled value is actually hit. The helper reads as intent and leaves no unused binding for a `no-unused-vars` rule to flag. Pair it with typescript-eslint's `switch-exhaustiveness-check` for fast in-editor feedback, but keep the `never` backstop: it survives a skipped lint step and also covers `if`/`else` chains and `Record` maps where a switch-only lint rule doesn't reach.
- **`satisfies` for config and literals — not `as`.** `satisfies` checks an expression against a type *without widening* it, keeping the narrow inferred type while still validating shape. Reach for it before an annotation (which widens) and far before an assertion (which lies). Use `const` type parameters to preserve literals through generics instead of sprinkling `as const`.
- **`as` is an unchecked claim — earn it or remove it.** A type assertion tells the compiler to stop checking; it generates no runtime guard and can be flat-out wrong. Replace assertions with type guards, narrowing, or validation. Every `as` (and especially `as any`) is a review checkpoint.
- **Non-null `!` is almost always a smell.** `value!` is a compile-time-only override with zero runtime safety; if you know it's non-null, the type system usually can too with a guard or a restructured flow. Treat each `!` as "why can't the checker prove this?"
- **`catch` is `unknown` — anything can be thrown.** Don't assume a caught value is an `Error`; narrow it before touching `.message`. For recoverable flows, prefer a typed `Result`/`Ok | Err` return that encodes failure in the signature over throwing.
- **Avoid `enum`; reach for `as const` objects or unions.** Runtime `enum` emits real objects, has surprising reverse-mapping and `const enum` inlining pitfalls, and bloats bundles. An `as const` object or a string-literal union expresses the same finite set with clearer semantics and no runtime cost.
- **Generics serve readability, not cleverness.** Deeply nested conditional and recursive mapped types that are harder to read than the logic they guard are a liability — they wreck compile times and IDE responsiveness and lock the code to a TypeScript expert. Extract complex types, comment them, and ask whether a plain type would do.
- **Template literal types for known, finite string sets only.** They shine on route patterns, event names, and CSS-class conventions where the set is static and small. Large interpolated unions explode compile time; pair any externally-sourced string with runtime validation regardless.
- **Configure modules for your bundler.** With a modern bundler set `moduleResolution: "bundler"`, `verbatimModuleSyntax: true`, and `isolatedModules: true` so imports behave as written, type-only imports stay erasable, and per-file transpilers (esbuild, swc) don't choke. TypeScript 7's native compiler is a drop-in performance upgrade — no semantic changes, so the same config carries over.

## Security

These are stack-specific failure modes on top of the language-agnostic security rules (trust boundaries, injection, secrets) and the JavaScript security rules (which apply in full — TypeScript compiles to JavaScript).

- **The type system provides zero runtime security.** Types, `as` casts, and `@ts-ignore` are erased before execution — an attacker can send a payload that satisfies the declared type yet carries malicious content. Authn, authz, and input validation must be enforced at runtime; never let a type signature stand in for a check.
- **`JSON.parse` returns `any` and bypasses every guard.** Parsed untrusted JSON enters the program untyped, so wrong types, extra fields, and prototype-polluting keys (`__proto__`, `constructor`) flow in unchecked. Validate the parsed value against a schema at the boundary before assigning it a trusted type.
- **`any` and unsafe casts erase security-relevant invariants.** Once user-controlled data is typed `any` (or asserted into a trusted type), the compiler can no longer distinguish "validated" from "raw attacker input." Keep untrusted values typed `unknown` until a guard or parser has actually checked them.
- **Third-party types can lie about runtime shape.** A `.d.ts` or `@types/*` package is a hand-written claim, not a verified contract — it may declare a non-null return that is actually `undefined`, or lag the library's real behaviour. Don't treat a declaration file as a runtime guarantee at a trust boundary; validate empirically and prefer libraries that ship their own inline types.
- **The npm dependency tree is the largest attack surface.** Typosquatted names, compromised releases, and `postinstall` scripts run with your privileges and can exfiltrate secrets at install time. Pin with a committed lockfile, install with `npm ci` and `ignore-scripts` in CI, minimize transitive depth, and screen packages (e.g. Socket) before adding them.
- **`verbatimModuleSyntax` keeps import intent honest.** Without explicit `import type`, the compiler's elision heuristics can drop an import whose only purpose is a runtime side effect (polyfill, global registration) — or accidentally retain a type-only one. Enabling it makes runtime-vs-type imports explicit and prevents that silent class of bug.
