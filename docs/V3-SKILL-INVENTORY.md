Counting commands (run from the repository root, bash):

```bash
for d in skills/*/; do
  n=$(basename "$d"); f="$d/SKILL.md"
  fm=$(awk '/^---$/{c++; next} c==1' "$f")
  ui=$(printf '%s\n' "$fm" | grep -m1 -E '^user-invocable:' | awk '{print $2}')
  lines=$(wc -l < "$f" | tr -d ' ')
  refb=0; refl=0
  if [ -d "$d/references" ]; then
    refb=$(find "$d/references" -type f -exec cat {} + | wc -c | tr -d ' ')
    refl=$(find "$d/references" -type f -exec cat {} + | wc -l | tr -d ' ')
  fi
  bang=$(grep -c '!`' "$f")
  hooks=$(printf '%s\n' "$fm" | grep -cE '^hooks:')
  dmi=$(printf '%s\n' "$fm" | grep -m1 -E '^disable-model-invocation:' | awk '{print $2}')
  at=$(printf '%s\n' "$fm" | grep -m1 -E '^allowed-tools:' | cut -c16-)
  echo "$n | ui=${ui:-unset} | lines=$lines | refs=${refb}B/${refl}L | bang=$bang | hooks=$hooks | dmi=${dmi:-unset} | at=${at}"
done
for f in agents/*.md; do echo "$(basename "$f" .md) | lines=$(wc -l < "$f" | tr -d ' ')"; done
```

The `!` block count is the number of lines containing `` !` `` in `SKILL.md`. Every hit was checked by reading the file, and all of them are real `!` blocks. Agent preloads come from each agent's `skills:` frontmatter list, and agent tool lists from its `tools:` list (section 6.1).

## 2. Criteria

### Disposition vocabulary

| Disposition | Meaning                                                                                         | Typical target                     |
| ----------- | ----------------------------------------------------------------------------------------------- | ---------------------------------- |
| stays       | Purpose and structure survive; may be renamed, trimmed under S1 and moved onto `ctx` `!` blocks | T42                                |
| merges      | Absorbed into another item; the row names the absorbing item                                    | T41 or T42, per the absorbing item |
| redesign    | Rewritten as a thin kernel-driven loop (`next` -> do -> report); most of its text is process    | T41                                |
| removed     | No v3 counterpart; the row names what replaces it (kernel command, CI test, nothing)            | T32 (deletion)                     |

A rename alone counts as "stays", with the new name in the target-name column.

### Process vs knowledge test

Applied per section of `SKILL.md` (and per `references/` file), counted in lines:

- **Process** moves to the artifact graph / kernel (T21-T23). It orders stages, decides what runs next, tracks or persists state, counts iterations or attempts, gates on approval, writes files at fixed paths, retries or escalates, or formats envelopes.
- **Knowledge** stays in the skill or a rule. It covers how to do the domain work well: heuristics, checklists, quality criteria, templates of the produced artifact and domain vocabulary.
- **Wiring** moves to `ctx` / frontmatter. It covers `!` blocks, settings lookups, tool-tier injection and `allowed-tools`.

**Process share** = process lines / `SKILL.md` lines. Above one half marks a redesign candidate. This is a guide for the rationale, not an automatic verdict. Every share below cites the line ranges classified as process.

### Evidence standard

Every rationale cites file and line. Where the v3 design and the code disagree, the code wins and the gap is listed under [Side findings](#10-side-findings).

## 4. Merge and rename candidates

### 4.1 `create-plan` + `verify-plan` -> `plan`

- **For**: `verify-plan` is 85% process (`verify-plan/SKILL.md:27-133`), and in v3 the kernel owns that process: budgets (T22), the verifier contract (P8) and plan-part validation replace the hash stamp (`:96-108`). The manual handoff between the two skills (`create-plan/SKILL.md:259-268`) becomes the graph's `next`. One stage skill per pipeline stage matches T41.
- **Against**: 285 + 133 lines of source. The merged skill meets S1 only if the process really leaves. Verification must stay an independent pass, which it does because the independence comes from the separate `plan-verifier` agent, not from a separate skill.
- **Recommendation**: merge (matches rows 3.2). Keep Phases 3-4 knowledge. The verify part shrinks to "dispatch `plan-verifier` when `next` says so, route its entries".

### 4.2 `add-rule` + `refine-rules` -> `rules`

- **For**: one body of knowledge (admission test, uniform format, linter), which `add-rule` already reads from `refine-rules` (`add-rule/SKILL.md:45,90,106,130`). T31 adds `bdk rules check`, and one skill as the user entry point to rules matches it.
- **Against**: different triggers ("capture this lesson" vs "clean up the directory"), so the merged skill must pick a mode from its argument. The two differ in invocation: `refine-rules` has DMI (`refine-rules/SKILL.md:6`), while `add-rule` has none and today triggers on natural phrases (`add-rule/SKILL.md:3`), and a merged skill has one frontmatter. `refine-rules` rewrites files, but it already asks for approval before writing (`:149-175`).
- **Recommendation**: merge into `rules` with two explicit modes (`add <lesson>`, `refine [dir]`) and no DMI, relying on the existing in-skill approval step for the destructive mode. Port the linter per OD-11.

### 4.3 `design` + `create-adr` (decision export)

- **For**: in v3 an accepted decision is a ledger entry (K1). An ADR is a rendering of one, so a separate capture skill duplicates the decision record.
- **Against**: today an ADR can be written without any design session (`create-adr/SKILL.md:20-45`). The MADR template adds ~50 lines to a skill already over S1. `docs/adr/` is a repository path, not a `.bdk/` artifact (`:48-52`).
- **Recommendation**: merge as export, with the MADR template moved into `design/references/`. Whether a stateless ADR path is still needed is OD-1.

### 4.4 Rename `test-driven-development` -> `tdd`

- **For**: short name, matches the design. The body is knowledge and survives as-is.
- **Against**: the rename touches the `implementer` preload (`agents/implementer.md:13`), its prose (`implementer.md:52,77`), the plan template lines (`create-plan/SKILL.md:239`, `create-plan/references/plan-template.md:163`), `subagent-execute-plan/SKILL.md:624` and `README.md:38`.
- **Recommendation**: rename in T42, updating every reference in the same change. Under the hard cut (Q1) there is no alias.

### 4.5 Rename `update-docs` -> `docs`

- **For**: short name, matches the design.
- **Against**: `docs` reads as "make docs", which is what `explain-complex-code` does. The two skills already share template, partition rules and an almost identical `Stop` hook (`update-docs/SKILL.md:9-14,65,163-187`, `explain-complex-code/SKILL.md:8-13`).
- **Recommendation**: rename. The overlap argues for merging `explain-complex-code` in as a create mode, which is a departure from the design and is left to the user as OD-13.

## 7. `cr` and `pr-review` package input

Constraint: neither skill's review logic changes (design "Problem", Out of scope). The cohorts, categories, merge, verdict policy and report format stay as they are. This section settles the design's open item "How `cr` and `pr-review` consume the dispatch package" (design "What We Did NOT Decide") as a proposal for T42.

**`cr`**

- **Input**: the `REVIEW_REQUEST` block (`cr/references/review-engine.md:19-33`) gains one optional field, `package: <path>`. When it is set, the engine passes four sections of the package to every reviewer as read-only context: intent summary, accepted decisions, assumptions and blockers (design "Dispatch package (K3, K4)"). These enter the reviewer prompt as a context block next to the existing range fields (`cr/references/reviewer-prompt-template.md`), outside the findings scope. The reviewer learns _why_ each change exists but does not review the decisions themselves.
- **Range**: `run_id` and `base_sha` come from the Change (T20) instead of `bdk_run_state.py list` (`cr/SKILL.md:62-64`).
- **Suppression and output**: the findings array keeps its shape. The orchestrator turns it into a `bdk-entries` block of `finding` entries and ingests it with `bdk log ingest --ticket` (T2). This replaces `bdk_run_state.py findings-add` and `findings-list` (`review-engine.md:171-180,214-236`). The suppression list becomes the Change's existing `finding` entries.
- **Without a package** (no Change, ad-hoc review), `cr` behaves exactly as today.

**`pr-review`**

- A PR under review usually has no Change on the reviewer's machine, so the package is optional and absent by default.
- When the PR's head branch carries a committed Change directory, the orchestrator builds the package from it and fills its path into template A's context (`pr-review/references/reviewer-prompt.md`). The subagent's `/bdk:cr --inline` run then receives it as `package:`.
- Posting, confirmation and verdict flow (`pr-review/SKILL.md:110-138`) are unchanged.
