# Agents

BDK ships eight subagents: seven thin adapters that run the role skills, and `bdk:web-researcher`. Every agent is invoked through the `Agent` tool with the `subagent_type` shown below, always in the namespaced form `bdk:<name>`. `STARTUP_INSTRUCTIONS.md` lists all of them in one table generated from the agent files. For how agents get resumed instead of respawned, see [Agents](../concepts/agents.md).

## Adapters

Seven thin adapters generated by `bdk export agents --host claude` and never edited by hand. Each binds a role to a tool set and a model; the role itself lives in a role skill under `skills/roles/` and in the dispatch package, so an adapter is frontmatter plus one sentence. BDK stage skills, `/bdk:cr` and the swarm skill start them with a dispatch package as the whole prompt; they are not picked for general tasks.

| `subagent_type`  | Model  | Effort | Tools                                                          | Roles                         |
| ---------------- | ------ | ------ | -------------------------------------------------------------- | ----------------------------- |
| `bdk:worker`     | sonnet | medium | Read, Edit, Write, Bash, Grep, Glob, SendMessage, Agent(scout) | `implementer`, `conformer`    |
| `bdk:reader`     | opus   | high   | Read, Write, Grep, Glob, Bash, SendMessage                     | `verifier`, `design-verifier` |
| `bdk:integrator` | opus   | high   | Read, Write, Grep, Glob, Bash, SendMessage                     | `integration-reviewer`        |
| `bdk:judge`      | sonnet | high   | Read, Write, Grep, Glob, Bash, SendMessage                     | `judge`                       |
| `bdk:reviewer`   | sonnet | medium | Read, Write, Grep, Glob, Bash, SendMessage                     | `reviewer`, `pr-reviewer`     |
| `bdk:runner`     | haiku  | none   | Read, Write, Bash, SendMessage                                 | `runner`                      |
| `bdk:scout`      | haiku  | none   | Read, Write, Grep, Glob, Bash, SendMessage                     | `scout`                       |

Haiku runs without an effort level, so `bdk:runner` and `bdk:scout` carry none. `bdk:integrator` has the tools, model and effort of `bdk:reader` but is its own adapter, so the integration reviewer's model can change without changing the verifiers. Only `bdk:worker` edits project files; the others write only their report draft under `.bdk/.machine/drafts/` (`guard/draft-only`). They carry `Bash` for BDK kernel commands and test runs, and every adapter carries `SendMessage` so an agent can reach `main` and any other agent by its id.

`/bdk:pr-review` starts the `pr-reviewer` role as a forked skill with a PR brief instead of a package; the role's frontmatter runs it on `bdk:reviewer`.

### The tree, the registry and messages

`main` starts every role agent: per plan part of a wave, one implementer that commits each task of the part, then one conformer. Of the adapters only `bdk:worker` starts agents, restricted to its `Agent(scout)` list, and `hooks pre-tool` enforces the same list (`guard/agent-spawn`): a worker may start a scout with a question, up to `agents.scout.max-per-ticket` per ticket. When a part uses up its attempts, its escalation ticket runs on `policy.escalation.model` (default `opus`) instead of the adapter's model: `bdk dispatch build` returns the model, the orchestrator passes it to the `Agent` call, and `hooks pre-tool` denies a start without it (`guard/escalation-model`).

The agent hooks record every agent in the registry `.bdk/.machine/agents.sqlite`: its parent, session, package, ticket and state (`starting`, `running`, `suspect`, `ended`). `bdk agents list` and `bdk agents show` read it; `bdk agents wait` returns when a child stores its report, sends a message, turns `suspect` or ends. A message between agents carries a ledger id and one sentence (`guard/agent-message`); the entry itself holds the content. See [Hooks](hooks.md) for the continuation check that sends an agent back when it ends its turn with work left.

## Read-only enforcement

No agent's frontmatter carries a `disallowed-tools` key. Read-only behaviour of `bdk:reader`, `bdk:integrator`, `bdk:judge`, `bdk:reviewer`, `bdk:runner`, `bdk:scout` and `bdk:web-researcher` comes from their `tools:` allowlist never granting `Edit`, `Write` or `NotebookEdit`.

The orchestrating skills add the same guarantee for their own turn: `/bdk:execute`, `/bdk:close` and `/bdk:pr-review` set `disallowed-tools: Edit Write NotebookEdit`, so the coordinator itself can change no file, and every change goes through a `bdk:worker` package or a kernel command. `/bdk:cr` sets `disallowed-tools: Edit NotebookEdit` and writes only its merged report's draft: while its review round is open, `hooks pre-tool` denies a main-thread edit outside `.bdk/.machine/drafts/` (`guard/draft-only`). See the [Skills reference](skills.md).
