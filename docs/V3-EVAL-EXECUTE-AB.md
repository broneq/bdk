# V3 eval: execute A/B

T40 (issue #60) measures whether a thin execute skill, one that loops `bdk next` and takes the order of steps from the kernel, does its job as well as a long skill that writes the order out (approach B). The outcome decides how T41 writes the stage skills. The criterion below was committed before the first measured run, so that the rows could not shape it; the results follow it.

## Setup

- Task: CSV export of the operator audit page in the fixture repository `kamkie/technical-interview-frontend` at `946a2081f84381ffc3b4a494467479a5b6886ead`; two plan parts, four test-first tasks (`evals/suites/execute-ab/task/`).
- Arms: `v2` (`/bdk:subagent-execute-plan` of tag `v2.7.0` on a v2 plan file), `v3-long` (`evals/suites/execute-ab/variants/execute-long/`), `v3-thin` (`evals/suites/execute-ab/variants/execute-thin/`, at most 200 lines).
- Cells: `v2`, `v3-long`, `v3-long-prime` (a second, identical `v3-long` cell: the A/A pair), `v3-thin`; 5 runs per cell, cells interleaved per run; orchestrator `claude-opus-5-5`.
- Metrics per run, computed from the state the session leaves, not from its own summary (`evals/suites/execute-ab/metrics.ts`):
  - **acceptance** (primary): the fixture's whole test suite, the hidden acceptance tests, `tsc -b` and lint on the changed files; the fraction that passes.
  - **completeness** (primary): the expected steps present, as a fraction. v3: per task a ticket, an implementer package, an implementer report, passing `simplify`, `tests-scoped` and `lint` evidence of a ticket closed `ok`, a commit with the task trailer; per part `part done`. v2: per group a commit with the run's trailers, a test-runner and a static-analyse spawn after the group's implementer; per task an implementer spawn; a run manifest with every group done.
  - secondary: cost, turns, wall time; v3 only: `bdk` calls, calls that exit 3, calls that exit 2, mean envelope length in bytes; the rubric (the final message states the recorded end state, judged by `claude-sonnet-5`).

## Criterion

Pre-registered before the first measured run (design D-7 of the OpenSpec change `v3-t40-promptfoo-harness`).

**Difference rule** (T03 D-7): a gap between two cells counts as measurable only when their medians are further apart than the larger of the two within-cell ranges. Otherwise the result is "no measurable difference". The A/A pair `v3-long` / `v3-long-prime` shows the noise floor of the setup.

**Decision**: thin is "no worse" when, on both primary metrics (acceptance and completeness), `v3-thin` vs `v3-long` is either "no measurable difference" or measurably in favour of `v3-thin`. Then T41 writes thin stage skills. Otherwise T41 falls back to approach B.

- A measurable regression of `v3-thin` on a secondary metric does not fail the criterion. It is listed for T41 with its cause, for example exit-3 calls that point at a thin instruction template.
- The `v2` comparisons decide nothing in T40. A measurable primary regression of `v3-long` vs `v2` is raised to the user as a v3 risk for T50.
- Discarded runs (provider error, failed isolation check, harness error, no reported cost) are not counted in any metric and are listed with their reason.
- The decision is read mechanically from the rows by `pnpm eval report execute-ab`; this report copies the numbers and the decision from its output.

### Decision

**Thin is "no worse": T41 writes thin stage skills.** On both primary metrics `v3-thin` vs `v3-long` is "no measurable difference", which the criterion accepts. The decision follows mechanically from the rows; the report generator prints it.

How to read it: four of the five `v3-thin` runs match `v3-long` exactly on both primary metrics (acceptance 1, completeness 1). The fifth (run 1) stopped after part 01: acceptance 0.75 (the hidden tests of part 02 fail), completeness 0.50, cost 0.88 USD, 38 kernel calls. That one run is the whole within-cell range, and the difference rule absorbs it. With 5 runs the rule cannot tell a 1-in-5 failure mode from noise, so the result is "thin is no worse at this sample size", not "thin never stops early".

### For T41

- **The early stop of `v3-thin` run 1.** After `bdk part done 01` the kernel answered `next: execute-part:02`, and `bdk next` returned `execute-part:02` as `ready`, so the kernel pointed the right way. The same `next` output listed the review gate as pending, with the finding "tiny Change outgrew its profile" and the command `/bdk:close`. The session ended with "I stopped at the end of part 01 because this command covered only that part". Every v3 run saw the same finding, and only this run stopped. Candidate fixes for T41: the thin skill states that one `/bdk:execute` runs every ready part and that a pending gate item does not end the loop; or the execute-part instruction's "When finished" line names `bdk next` as the step after `part done`.
- **Exit 3 calls.** `v3-thin` median 3 vs `v3-long` 1, no measurable difference (the A/A pair alone spans 1 to 3). Not a finding at this sample size.
- **Turns.** `v3-thin` median 43 vs 36, no measurable difference; a thin skill makes the orchestrator ask the kernel more often, at no measurable cost.

### Kernel effect (v3-long vs v2)

No measurable primary regression of `v3-long` vs `v2`, so nothing is raised as a v3 risk for T50.

- **Completeness: `v3-long` higher** (1 vs 0.76). The v2 metric expects a test-runner and a static-analyse spawn after each group. The v2.7.0 skill leaves that cadence to the orchestrator's judgment ("max 2 consecutive skips"), and the runs verified once per two groups, which the tagged skill allows. The gap therefore measures the kernel's enforced per-ticket evidence against v2's judgment-based cadence, not v2 skipping a step its own contract requires.
- **Cost: `v2` higher** (3.90 vs 1.59 USD, about 2.5 times). The v2 runs also spawned review agents (`code-reviewer`, `duplicate-detector`, `dead-code-detector`, `fixer`) inside the execute run, which the v3 pipeline leaves to its later review stage, so the cost gap is partly a scope difference of the two execute stages.
- **Acceptance**: all v2 and `v3-long` runs pass everything.

### Rubric

All 20 runs have rubric 1. The rubric was regraded after the series: its first judge failed 4 of the 5 `v3-thin` runs for details that the recorded end state cannot confirm (commit hashes, check results), while their end state matched the message. The system text was fixed to judge only what the state records, all 20 runs were regraded from their saved judge requests, and the first answers are kept next to them (design D-2 "As built (rubric)"). The rubric is reported, not part of the decision.
