# BDK v3 design - decyzje z kroku 1 (Lavish .lavish/bdk-v3-design-01-produkt.html), 2026-09-22

## Decyzje produktowe
- D1 Centralny obiekt: **Zmiana** (ID od intencji; trzyma intencję, rejestr decyzji, design, graf części planu, runy, review). Odrzucone: pipeline etapów, graf ticketów.
- D2 Kierunek **OpenSpec**: żywy spec + Zmiana z deltami, merge do specu przy zamknięciu, archiwum.
  - D2a Żywy spec = **tylko zachowanie** (Requirement/Scenario, jak OpenSpec). Wbrew rekomendacji. Konsekwencja: S4 (wzorce przy planie) opiera się na regułach projektu z ID + archiwum designów; reguły projektu muszą móc być konkretne dla systemu. Ryzyko do "Czego nie zdecydowaliśmy": jeśli reguły za ogólne -> wrócić do specu architektonicznego.
  - D2b **Wiedza Zmiany commitowana** (spec, intencja, rejestr decyzji, design, delty, części planu, archiwum); **stan maszynowy lokalny** (liczniki prób, czasy, sesja, cache), gitignorowany, odtwarzalny z trailerów gdzie możliwe. Naprawić defekt ensure_ignored() `/.bdk/` -> `/.bdk/runs/`-like.
  - Z raportu C1-C3: merge skryptem deterministycznie (LLM tylko przy konflikcie), walidator semantyki (prefiks Scenario:, WHEN/THEN, utrata scenariuszy = ERROR, słowo normatywne konfigurowalne), hook blokujący ręczną edycję specu, opt-out `spec-impact: none` wymagany.
- D3 Autonomia: **polityka projektu**, domyślnie bramki człowieka na designie i review końcowym; decyzje bez nadzoru -> rejestr "do przejrzenia"; bramki egzekwuje rdzeń.
- D4 Konfiguracja osobista: **pełne nadpisanie** (wbrew rekomendacji). D4b: rdzeń zapisuje w Zmianie listę nadpisanych kluczy (bez wartości) przy starcie runu; review dostaje ją w podsumowaniu.
- D5 Runtime rdzenia: **Node, TypeScript jako źródło, bundel ESM commitowany i pilnowany `git diff --exit-code` na CI, node --test, Biome; reguły ADR 0001 git-identity poza regułą 9**; rdzeń bez runtime'u = głośny błąd z instrukcją instalacji. Konsekwencje: dwa runtime'y u użytkownika (node + uv dla MCP), aktualizacja ADR 0001 ("bdk stays in Python" nieaktualne), twarde cięcie v2->v3, porting testów.

### Decyzje T1-T6
- T1 Dowód zgody na bramce: **A-lite, bez hashy i bez formalnego zatwierdzania** (wersja ze strony 07 skorygowana na stronie 08) - bramkę przechodzi wpisanie przez człowieka komendy następnego etapu (`/bdk:plan` po designie, `/bdk:close` po review). Skille etapów `plan`, `execute`, `close` mają `disable-model-invocation: true` (pole hosta: tylko użytkownik może je uruchomić), a hook `UserPromptExpansion` (odpala się wyłącznie dla komend wpisanych przez człowieka) woła `bdk hooks prompt-expansion`, który zapisuje w dzienniku wpis `transition` ze stemplem `source: user` (zegar rdzenia, `session_id`, treść komendy, flaga `--skip-verify` z P2). Węzeł bramki jest gotowy, gdy taki wpis istnieje. Bez hashy artefaktów, bez rekordów zgody `approvals/`, bez ponownego zatwierdzania po zmianie, bez dyspozycji wpisów `review: true` (status bramki tylko je pokazuje w chwili wpisywania komendy), bez `doctor --audit`, bez komendy `approve`. Bramka wiąże się z chwilą wpisania, nie z treścią: edycja designu po wpisaniu `/bdk:plan` nie blokuje niczego (świadomie zaakceptowane ryzyko, widoczne przez checkpoint commity). `/bdk:execute` nie jest bramką; D3 zostaje przy dwóch bramkach. Bash na `bdk.mjs hooks` = deny (druga linia obrony). Nowe kryterium sukcesu S8. Odrzucone: A pełne (osobna komenda approve), wariant z hashem pokazanym lub wpisywanym (strona 08: "żadnych hashy z potwierdzeniem jednak nie robił - to nie ma sensu dla mnie"), trzecia bramka na `execute` (strona 08: "nie chcę formalnego zatwierdzania"), przechwycenie AskUserQuestion, rekord pisany przez model, pominięcie (wymagałoby przepisania D3 na "bramki egzekwuje model").

Odrzucone: A (rdzeń jako wąski serwer MCP z `log_add`, `log_show`, `report_write`, `dispatch_show`; zapisane jako wyzwalacz do powrotu, jeśli przekaźnik przez orkiestratora będzie mierzalnie gubić lub rozdymać wpisy), B (przechwycenie SubagentHandback; narzędzie istnieje tylko w auto mode), C (Bash dla wszystkich).
