1. Format konfiguracji: jeden projekt, trzy zapisy

Przykładowy projekt: TypeScript z vitest, eslint i tsc, włączony code-review-graph, projekt chce dodać własną bramkę po planie, podnieść budżet fixów, dopisać dwie reguły projektowe i podać agentom opis celu produktu oraz dodatkową instrukcję dla implementera. Osoba pracująca w projekcie chce po polsku i z Lavish. Treść jest identyczna w każdym wariancie, różni się tylko zapis.

Wariant 1: YAML na strukturę + katalog prompts/ na tekst rekomendacja

.bdk/settings.yaml (projekt, commitowane)

# schemat: bdk config schema  |  walidacja: bdk config check
bdk: 3

features:
  code-review-graph: true
  serena: false

tools:
  test:
    - id: vitest          # tablice łączone po id (B7)
      tier: fast
      full: npm run test:unit
      scoped: npx vitest run {files}
      related: npx vitest related --run {files}
      failed: npx vitest run --changed
  lint:
    - { id: eslint, tier: lint, full: npm run lint, scoped: npx eslint {files} }
    - { id: tsc, tier: typecheck, full: npm run typecheck, incremental: npx tsc -b --incremental }

policy:
  gates:
    - id: after-plan        # węzeł grafu dodany przez projekt
      after: plan
      who: human

    review-fix: 3          # domyślnie 2
  escalation:
    stronger-model: true

rules:
  project: .bdk/rules/       # pliki .md z ID, mode w ich frontmatterze

D4b: 1 klucz nadpisany lokalnie w tej Zmianie

Ocena. Tekst ma podświetlanie, diff per plik, frontmatter mówi, gdzie stosować. Struktura ma komentarze i schemat. Nazwa pliku jest kluczem, więc warstwowanie i D4b działają jednakowo dla tekstu i dla flag. Koszt: dwa miejsca, dlatego bdk config show pokazuje pochodzenie. Reguły projektu to ten sam mechanizm, tylko z ID w treści.

Ocena. Jeden plik, jedna składnia, nic do szukania. To, co widzisz po lewej, to już 40 linii przy dwóch tekstach i jednej regule; realny projekt z opisem celu, pięcioma tekstami dla ról i kilkoma plikami reguł ma 200-400 linii, czyli rozmiar dzisiejszego planu, którego chcieliśmy się pozbyć.

Konkretne koszty: Markdown w bloku | nie ma podświetlania w edytorze; wcięcie bloku zjada wcięcia list Markdown, więc listy zagnieżdżone i bloki kodu w tekście łatwo popsuć; diff zmiany w tekście miesza się z diffem flag; mode i applies muszą być rodzeństwem text, więc każdy tekst to trzy klucze zamiast jednego pliku.

Zalety, których wariant 1 nie ma: całość jednym cat; jeden schemat waliduje wszystko, także teksty.

Wariant 3: Markdown z frontmatterem jako jedyny format

# .bdk/settings.md
---
bdk: 3
features: { code-review-graph: true, serena: false }
tools:
  test:
    - { id: vitest, tier: fast, full: npm run test:unit,
        scoped: npx vitest run {files} }
  lint:
    - { id: eslint, tier: lint, full: npm run lint, scoped: npx eslint {files} }
policy:
  gates: [{ id: after-plan, after: plan, who: human }]
  budgets: { review-fix: 3 }
---

## project.goal

Panel administracyjny dla operatorów sieci ładowarek.
Priorytet: poprawność rozliczeń nad wygodą UI.

## role.worker.extra {mode=extends applies=implementer,fixer}

### Konwencje tego repo

- Błędy domenowe dziedziczą z `AppError` (`src/errors.ts`),
  nigdy gołe `throw new Error`.
- Każdy nowy endpoint ma test kontraktu w `tests/contract/`.

## rules.api-errors {mode=extends}

- **[API-1] Kody błędów.** Każda odpowiedź 4xx niesie `code`
  z `ErrorCode`; brak kodu = bug, nie styl.
- **[API-2] Brak wycieków.** Komunikat 5xx nigdy nie zawiera
  ścieżek ani stack trace.

Ocena. Wygląda jak SKILL.md i agent.md, więc jest znajome. Tekst ma pełne podświetlanie. Jeden plik.

Koszty: nagłówek ## pełni rolę klucza, więc tekst nie może sam używać ## (w przykładzie musiałem zejść do ###); atrybuty w klamrach po nagłówku to własna mini-składnia, którą trzeba parsować i dokumentować; frontmatter rośnie do 60-100 linii YAML dla realnego projektu i przestaje być "front"; merge warstw po nagłówkach jest kruchy (zmiana nazwy sekcji w projekcie cicho odłącza nadpisanie osoby); jeden plik miesza zmiany flag i tekstu w diffie, tak jak wariant 2.

Reguły z ID w tym wariancie tracą frontmatter per plik, więc mode ląduje w klamrze.

Dla kontrastu: dzisiejszy JSON z tym samym tekstem

{ "prompts": { "role.worker.extra": { "mode": "extends", "text": "## Konwencje tego repo\n\n- Błędy domenowe dziedziczą z `AppError` (`src/errors.ts`),\n  nigdy gołe `throw new Error`.\n- Każdy nowy endpoint ma test kontraktu w `tests/contract/`.\n" } } }

Bez komentarzy, jedna linia, każdy cudzysłów w tekście do escapowania. To jest powód, dla którego dzisiejsze quality.* już wskazuje na pliki .md zamiast trzymać tekst w JSON.

Format konfiguracji zdecydowane

Wariant 1. YAML na strukturę (settings.yaml, settings.local.yaml, ~/.config/bdk/settings.yaml) plus katalogi prompts/ i prompts.local/ z plikami Markdown jako kluczami i frontmatterem mode/applies; reguły projektu jako pliki Markdown z ID w .bdk/rules/. Warunek z Twojej uwagi: schemat dla IDE, opisany niżej.

Schemat YAML dla IDE: tak, i to z jednego źródła

YAML nie ma własnego języka schematów, ale edytory walidują YAML JSON Schema: VS Code przez rozszerzenie Red Hat YAML (yaml-language-server), JetBrains wbudowanie (mapowanie schematów JSON na pliki YAML). Oba rozumieją modeline w pierwszej linii pliku, więc plik sam mówi, którym schematem go sprawdzać, bez konfiguracji edytora.

pierwsza linia .bdk/settings.yaml (dopisuje bdk setup)

# yaml-language-server: $schema=https://raw.githubusercontent.com/broneq/bdk/v3.0.0/schema/settings.schema.json
bdk: 3
...

Wersja w URL jest przypięta do wersji pluginu, więc podpowiedzi zgadzają się z tym, co rdzeń akceptuje. Kopia offline w .bdk/.machine/schema/; bdk setup może przepiąć modeline na nią flagą --offline-schema.

  • Jedno źródło prawdy. Schemat zod w rdzeniu (ten, który waliduje przy bdk config check) jest eksportowany do JSON Schema (zod 4 ma wbudowany eksport) na CI i commitowany do schema/; test CI pilnuje, że plik jest aktualny (git diff --exit-code, jak bundel). Rejestr schematów per moduł (B9) składa się w jeden dokument z $defs.
  • Co dostaje IDE. Podpowiedzi kluczy, enumy (tier, who, typy wpisów), opisy z .describe() jako hover, podkreślenie nieznanych kluczy, wymagane pola.
  • Czego IDE nie sprawdzi. Reguł między plikami: czy policy.gates[].after wskazuje istniejący węzeł, czy {files} jest w komendzie scoped, czy plik prompts/*.md ma poprawny frontmatter. To robi bdk config check, uruchamiany też w hooku SessionStart w trybie tylko-ostrzeżenie.
  • Frontmatter w plikach .md (prompts, reguły, wpisy dziennika) ma osobne schematy w tym samym rejestrze; IDE ich nie zastosuje automatycznie, więc tu bdk config check i bdk log check są jedyną walidacją.

2. Kontrakt CLI w zarysie

To jest zarys grup poleceń i zasad, nie pełna specyfikacja; pełny kontrakt (kształty JSON, kody błędów, przykłady) powstaje jako pierwszy artefakt planu, bo od niego zależą testy rdzenia i treść skilli. Każde polecenie ma --json. Bloki ! wołają zawsze bdk ctx lub bdk next, nigdy polecenia zmieniające stan.

Dwa tryby wyjścia

Inject (ctx, next z bloku !): zawsze exit 0; błąd to blok "BDK STOP: <powód> <co zrobić>" w treści, bo host gubi wyjście przy exit != 0. Polecenie (wszystko z Bash): exit 0 sukces, 2 odmowa (Refusal), 3 błąd wejścia, 4 stan uszkodzony (fail-closed, wskazuje rebuild), 5 brak runtime lub wersji.

Odmowa

Ten sam kształt wszędzie: refused, rule (np. attempt.budget), why jedna linia, instead lista poleceń do wykonania zamiast. Skill nie interpretuje, tylko wykonuje instead albo pyta człowieka, gdy lista jest pusta.

Wycinki, nie całość

status, log list, part list zwracają domyślnie do 100 linii i mają --for <task|part|plik>; pełna treść tylko przez show <id>. Odmowa przy próbie zrzutu całego stanu bez --all.

5. Dwa pytania, które odsłoniły ostatnie decyzje

Profil skali zdecydowane

Pomiar + nadpisanie. Rdzeń proponuje profil z pomiaru (pliki z intencji, wpływ z grafu kodu, dotknięte moduły), zapisuje jako wpis assumption; człowiek lub polityka nadpisuje flagą --profile; zmiana w trakcie tylko w górę. Heurystyka do kalibracji na fiksturze, trafia do "Czego nie zdecydowaliśmy".

Identyfikatory reguł zdecydowane

Prefiks pliku + numer nadany raz: [CQ-4], [ARCH-2], [API-1]. Numer nigdy nie jest reużywany; usunięta reguła zostaje jako wpis "(usunięta: powód)"; bdk rules check pilnuje unikalności i formatu. Cytaty w findingach i checklistach po ID, treść przez bdk rules show.

6. Dolt jako magazyn stanu? Twoje pytanie

Dolt to baza SQL (MySQL-kompatybilna) z semantyką gita na poziomie wierszy: commit, branch, merge, diff i blame na danych. Pytanie brzmi: czy trzymać w nim dziennik, stan Zmian i próby zamiast w plikach Markdown plus lokalnym indeksie. Rozbijam na to, co Dolt daje, co kosztuje w naszym układzie i czym da się dostać 90% korzyści.

Co Dolt daje naprawdę

  • SQL po całym stanie: "pokaż findingi typu security z ostatnich 5 Zmian, które wróciły po fixie" to jedno zapytanie.
  • Historia i diff na poziomie wiersza, dolt blame na decyzji.
  • Branch i merge danych, gdy dwie osoby piszą do tej samej Zmiany (Q2b w przyszłości).
  • Jedna spójna transakcja zamiast wielu plików.

Co kosztuje u nas

  • Drugi runtime. Binarka Go około 100 MB, instalacja per maszyna i CI; łamie zasadę D5 "tylko Node" i regułę ADR 0001 o zachowaniu przy brakującym runtime.
  • Drugi system wersji. Commit gita i commit Dolta trzeba spinać (który stan Dolta odpowiada któremu SHA); dziś prawdą są trailery w gicie, Dolt rozbiłby to na dwie prawdy.
  • Wiedza znika z PR. D2b mówi: wiedza commitowana jako Markdown, czytelna w diffie PR i przez grep. Dane w Dolcie są w jego formacie; do PR trzeba eksportować, do agentów tłumaczyć przez SQL.
  • Współdzielenie. Zespół potrzebuje zdalnego Dolta (DoltHub lub własny) albo commitowania katalogu .dolt/ (binarny, duży) w gicie.
  • Skala nie wymaga. Zmiana ma setki wpisów, projekt tysiące; to rozmiar, który SQLite w pamięci przeszukuje w milisekundach.

90% korzyści bez Dolta

  • Indeks SQLite w .machine/ budowany z plików Markdown przez node:sqlite (wbudowane w Node, bez zależności; status stabilności do potwierdzenia dla wersji minimalnej). Rebuildowalny, gitignorowany, jak cały .machine/.
  • bdk query "<sql>" tylko do odczytu, do szukania błędów i raportów; te same tabele zasilają log list --for i detekcję oscylacji.
  • Historia i blame: git na plikach wpisów, bo każdy wpis to plik (K4), a decyzja zmieniona to nowy wpis z supersedes.
  • Branch i merge danych: git, bo katalog Zmiany jest w repo; walidator konfliktów wpisów to funkcja odłożona w Q2b.

Moja ocena. Dolt jest właściwym narzędziem, gdy dane same są produktem i wielu pisarzy musi je gałęziować i mergować niezależnie od kodu. U nas dane są śladem pracy nad kodem, żyją obok kodu i mają być czytelne w tym samym PR. Wprowadzenie Dolta to przerost formy: drugi runtime i druga oś wersji za funkcje, które w 90% daje indeks SQLite nad plikami. Zostawiam furtkę: rdzeń czyta stan przez jeden moduł "store", więc gdy kiedyś pojawi się potrzeba wielu równoległych pisarzy na jednej Zmianie, wymiana magazynu nie dotyka skilli ani kontraktu CLI.
