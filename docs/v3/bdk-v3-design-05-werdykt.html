2. Iteracja 2: PASS_WITH_WARNINGS

Ostrzeżenia rozwiązane mechanicznie

  • Zły event dla checkpointu. W Claude Code Stop odpala się po każdej turze, nie na końcu sesji; commit mógłby wyścigować z subagentami i zgarnąć pliki, które użytkownik miał w indeksie. Poprawka: event SessionEnd, commit pathspec git commit --only -- .bdk/changes/<id>/, pomijany w trakcie rebase/merge i przy otwartych biletach.
  • Alokator ID nie przeżywał świeżego klona (git nie śledzi pustych katalogów). Poprawka: najpierw maksimum z commitowanych plików, potem blokada w .machine/.
  • Tabela hooków poprawiona na faktach: create-plan ma tylko mkdir -p .bdk/plans (znika), update-docs i explain-complex-code mają hooki typu prompt (bez zmian), is-command-exists nie jest używany przez żaden skill (usuwany, nie portowany).
  • Składnia bloku ! w prawdziwej formie inline; reguła allowed-tools na node; do sprawdzenia na żywo, czy reguła preaprobuje złożone polecenie z ||.
  • Zdania sprzeczne ze zmianami wyczyszczone (spec, wiersz SPOF, migracja, testy CI).

Dwie rzeczy, które weryfikator słusznie oddał Tobie

  • Automatyczne commity checkpoint na Twojej gałęzi. Mechanizm jest bezpieczny (pathspec, pomijanie przy rebase), ale to nadal commit, którego nie robisz ręcznie. Pytanie 2.
  • Śledzenie plików design w tym repo. .gitignore BDK ma /.bdk/ i /.lavish/, więc ani dokument, ani rejestr decyzji, ani strony Lavish nie są dziś śledzone. To ten sam defekt ensure_ignored(), który v3 naprawia. Pytanie 3.

Oceny weryfikatora po iteracji 2: zgodność z kodem WARNING 0.80, adwokat diabła PASS 0.88, pokrycie wymagań WARNING 0.68, diagramy PASS 0.88, uczciwość WARNING 0.70. Ostrzeżenia dotyczyły dokładnie punktów powyżej, wszystkie są już w szkicu.
